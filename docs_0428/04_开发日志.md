# 开发日志

## 2026-04-28：phase3 direct encode 多输入模式串扰修复

### 背景

`0428` 目录已经将 `phase3 direct encode` 固化为当前唯一继续演进的 `phase3` 主方案，
并且已经完成：

- `tp4` 启动与稳定运行
- `local_path` 支持
- `http` 支持
- 视频 fallback 到 stock 路径
- `L0 / L0.5 / MME / MMBench` 多轮精度回归

但在继续做 `http / base64 / local_path` 三种输入模式切换测试时，
暴露出一个新的系统性问题：

- 同一个服务进程内，先跑 `http`，再跑 `base64` 或 `local_path`
- 会偶发出现把历史 `http` 输入残留状态错误复用到后续请求的现象
- 具体外显包括：
  - `base64 MMBench` 请求中错误访问 `http://127.0.0.1:9000/mmbench/*.jpg`
  - 返回 `404`
  - 上层继续放大后出现 `500 InternalServerError`
  - 某些场景下会进一步触发 `encoder cache miss`

### 原方案的问题

原始 patch 的重点在于两件事：

1. 为 `local_path` 透传本地路径，支撑 `phase3 direct encode`
2. 为 worker 侧 direct encode 提供足够的定位信息

这套实现对 `local_path -> worker direct encode` 主链路是成立的，
但它存在一个隐含前提：

- “同一张图的传输方式不会变化”

而精度测试恰好打破了这个前提：

- 同一个数据集文件
- 可能先以 `http://127.0.0.1:9000/mmbench/1986.jpg` 发起
- 再以 `data:image/...;base64,...` 发起
- 再以 `file:///.../mmbench/1986.jpg` 或本地路径发起

旧方案的问题不是 direct encode 算法本身，
而是 **传输层 identity 没有被显式建模并传到底层**。

旧 patch 更多是在传：

- `_phase2_local_path`
- `phase2_local_mm_paths`
- `phase3_local_mm_ready`

但没有稳定传递：

- 当前输入到底是 `local_path / http / base64` 中的哪一种
- 它的 source key 是什么
- 哪些 key 允许跨请求复用
- 哪些 key 只允许 request-scope 使用

这样一来，只要底层某处还存在“按逻辑名、相对路径、历史 url 映射、旧请求残留状态”做弱关联的机会，
就有可能把：

- `mmbench/1986.jpg -> http://127.0.0.1:9000/mmbench/1986.jpg`

错误复用到后续 `base64` 或 `local_path` 请求上，
从而形成跨输入模式串扰。

### 已观测到的现象

在 `0428 phase3 direct encode tp4` 环境下，已经确认：

1. `base64 MMBench` 曾出现 `404/500`
   现象是请求不该再访问本地静态 HTTP 服务，但日志里仍出现
   `127.0.0.1:9000/mmbench/*.jpg`。

2. `local_path MMBench` 曾出现 `500`
   放大后表现为 `encoder cache miss / EngineDeadError / 500`。

3. 做“切换输入模式前重启服务”后，问题可消失
   说明这是 **进程内跨请求状态污染/弱 key 复用问题**，
   而不是数据集本身错误。

### 已验证的临时规避方案

临时规避方案已经验证有效：

- 在切换多模态输入模式前重启服务

重启后已经验证：

- `base64 MMBench` 可跑通，不再出现错误访问 `9000/mmbench/*.jpg`
- `base64 MMBench` 不再出现 `404 / 500 / encoder cache miss`
- `local_path MMBench` 可跑通，不再出现 `500 / EngineDeadError`

这说明当前问题不是模型精度问题，
而是输入模式切换时的 transport-layer identity 污染问题。

### 修复目标

修复目标不是“让不同输入模式互相复用同一份缓存”，而是：

1. 明确区分 `local_path / http / base64`
2. 禁止不同输入模式之间的弱关联复用
3. 保持 `phase3 direct encode` 对 `local_path` 和可支持 `http` 路径的主能力
4. 不修改 vLLM 源码，只修改 `0428/patch`
5. 不引入高成本内容 hash

### 为什么不采用内容 hash

这里不采用“按图像内容本体做 hash”的原因有三点：

1. 成本高
   对每张图都读取完整内容再 hash，会明显增加 API server 热点负担，
   与当前“把热点下沉、让 API server 只保留编排职责”的目标相冲突。

2. 真实业务收益低
   真实生产里，同一份图像数据同时既用 `local_path` 又用 `http`
   又用 `base64` 去请求，通常不是主流场景。

3. 当前问题本质不是“同内容去重失败”
   而是“不同输入模式被错误混用”。
   因此更应该修 transport identity，
   而不是做昂贵内容去重。

### 新方案

本次修复采用 **source-based identity**：

- 不按图像内容做 hash
- 按“输入模式 + 来源信息”生成稳定 key

具体规则如下。

#### 1. local_path

`local_path` 的 source key 采用：

- `media_mode=local_path`
- `realpath`
- `stat.st_size`
- `stat.st_mtime_ns`

目标：

- 同一路径文件变更后 key 会变化
- 不同路径不会误判为同一资源
- 不需要读取图像全部内容

#### 2. http

`http` 的 source key 采用：

- `media_mode=http`
- canonical url

目标：

- 不与 `local_path` 共用 identity
- 不与 `base64` 共用 identity

#### 3. base64

`base64` 不做跨请求稳定缓存 key，
只做 **request-scope key**：

- `media_mode=base64`
- `request_scope`
- `image index`

例如：

- `req:<request_id>:image:0`
- `req:<request_id>:image:1`

目标：

- `base64` 只在单请求内部保持一致
- 不与历史 `http` 或 `local_path` 请求发生弱关联

### 关键设计原则

#### 原则 1：transport mode 是 identity 的一部分

即使它们最终指向“同一张图”，下面三种输入也视为不同 source：

- `local_path`
- `http`
- `base64`

不允许仅因为逻辑名相同，例如 `mmbench/1986.jpg`，
就在不同模式之间复用。

#### 原则 2：禁止跨模式 fallback

后续任何映射、回填、恢复、兜底逻辑都必须满足：

- 当前请求的 `media_mode`
- 已存状态的 `media_mode`

二者一致时才允许复用；
只要 mode 不一致，就必须当作 miss 处理。

#### 原则 3：bare logical name 不能作为稳定 key

以下信息都不能单独作为稳定 identity：

- `mmbench/1986.jpg`
- 相对路径
- 不带 mode 的 url 尾部

这些值最多只能作为调试信息，不能作为跨请求复用主键。

### patch 层落点

本次修改只允许发生在 `0428` 下，不修改 vLLM 源码。

预计落点：

- `bundle/vllm_phase2_plugin/patches/phase1.py`
- `bundle/vllm_phase2_plugin/common/mm.py`
- 如有必要，补充 `patches/phase2.py` 的 metadata 透传

### 方案摘要

最终方案可概括为：

1. 在 parser 入口识别 image 输入模式
2. 生成带 mode 的 `source_key`
3. 为 image 显式生成 `uuid`
4. 将 `uuid/source metadata` 随 `multi_modal_uuids` 与 patch metadata 一起向后透传
5. `base64` 使用 request-scope uuid
6. `local/http/base64` 之间禁止通过弱 identity 互相复用

### 回归验证要求

修复完成后，至少需要确认：

1. 不重启服务，先跑 `http` 再跑 `base64 MMBench`
   不应再访问 `127.0.0.1:9000/mmbench/*.jpg`
   不应再出现 `404 / 500`

2. 不重启服务，先跑 `http` 再跑 `local_path`
   不应把 HTTP 历史状态错误复用到本地路径请求

3. `phase3 direct encode tp4` 的基本精度能力不回退
   重点关注：
   - `L0`
   - `L0.5`
   - `MME`
   - 必要时复测 `MMBench`

### 当前结论

到本次日志记录时，已经形成明确结论：

- 问题属于多模态输入 transport identity 串扰
- 不是 direct encode 主算法错误
- 不需要修改 vLLM 源码
- 最合理的修复方式是：
  - 在 `0428` patch 层显式生成 mode-aware uuid/source key
  - 禁止跨模式 fallback
  - `base64` 只做 request-scope 复用

## 2026-04-28：phase4 HTTP 输入本地缓存池优化

### 背景

`0428` 当前已经把 `phase3 direct encode` 固化为主方案，但它对不同输入模式的收益并不一致：

- `local_path` 已经能稳定复用 worker 侧 direct encode 主链路
- `http` 虽然功能上可用，但更多还是 stock 行为兼容

因此需要引入新的 `phase4`，专门解决：

`让 http 输入也能复用 phase3 direct encode 的收益。`

### 反推后的问题本质

`phase3 direct encode` 的核心前提是：

- API 侧能把图片输入表达成“可透传本地路径的 phase3 引用”

`local_path` 天然满足这个条件；
而 `http` 不满足，所以在 `phase3` 中：

- 不能设置稳定的 `_phase2_local_path`
- `phase3_local_mm_ready` 不会被置为 `true`
- worker 就无法复用现有的本地路径 direct encode 主链路

### 方案选择

这里有两个备选方案：

1. worker 自己下载远端 http 资源
2. API server 先下载到本地缓存池，再当作 local_path 走 phase3

最终选择方案2，原因是：

1. 可以最大化复用现有 `phase3 direct encode`
2. 下载、锁、TTL、大小限制都更容易统一收敛
3. 风险更低，不需要在 worker 再发明一条远端抓图链路

### 新方案定义

`phase4 = API server 本地 HTTP cache pool + materialize 到本地文件 + 复用 phase3 direct encode`

也就是：

1. 识别 `http/https` 图片 URL
2. 以 canonical URL 计算 cache key
3. 命中则复用缓存
4. miss 则下载到本地缓存目录
5. 下载成功后构造 phase3-style local image ref
6. worker 继续走原有 direct encode

### 关键设计原则

#### 原则 1：只在 phase4 生效

所有新逻辑只允许在：

```text
VLLM_ASCEND_API_OPT_PHASE >= 4
```

时启用，保证 `phase0 ~ phase3` 完全不受影响。

#### 原则 2：transport identity 不变

缓存到本地后，仍保留：

- `media_mode=http`
- `image_url=<original http url>`

只是额外补上：

- `_phase2_local_path=<cached local file>`

这样既能让 worker 复用本地 direct encode，
又不会把它错误伪装成用户本来就是 `local_path`。

#### 原则 3：不做内容 hash

仍然坚持“按来源标识，不按图像内容全文 hash”的方向：

- `cache_key = sha1(canonical_http_url)`

原因：

1. 成本更低
2. 更符合真实业务中“同 URL 重复请求”的场景
3. 避免重新把热点拉回 API server

### 本次代码改动

#### `bundle/vllm_phase2_plugin/patches/phase1.py`

新增或补齐：

1. `phase4` 环境开关
2. HTTP cache 目录、TTL、超时、大小限制、chunk 大小、UA 配置
3. 基于文件锁的 HTTP 物化逻辑
4. `http -> local cached file -> phase3-style ref` 组装逻辑
5. 在下面几个入口接线：
   - `MultiModalContentParser.parse_image`
   - `AsyncMultiModalContentParser._image_with_uuid_async`
   - `MediaConnector.fetch_image`
   - `MediaConnector.fetch_image_async`

#### `bundle/vllm_phase2_plugin/common/mm.py`

补充 `image_url` 元数据透传，方便 trace/validate/debug。

#### `bundle/start_phase4_server.sh`

新增 `phase4` 启动脚本，便于直接拉起：

```bash
export VLLM_ASCEND_API_OPT_PHASE=4
```

### 预期收益

完成后，`http` 输入将具备两层收益：

1. 相同 URL 的重复请求可以命中 API 侧本地缓存
2. materialize 完成后，worker 可以复用已有的 `phase3 direct encode`

### 验证计划

本阶段验证顺序：

1. 启动 `phase4 tp4`
2. 用 `http` 输入跑 `L0`
3. 用 `http` 输入跑 `L0.5`
4. 用 `http` 输入跑 `MME`

重点关注：

1. 是否出现 `phase4_http_cache_fill/hit`
2. 是否进入 `api_parse_image_phase4_http_ref`
3. worker 是否进入 `worker_phase3_direct_encode`
4. 精度是否通过

## 2026-04-28：phase4 HTTP 输入性能验证

### 背景

在 `phase4` 功能与精度验证基本符合预期后，需要继续确认：

- `phase4` 在 `http` 输入模式下的时延口径
- API server / engine core / tp worker 的热点是否符合预期
- `phase4` 的主要收益点是不是确实集中在“把 HTTP 输入接入更优链路”，而不是误以为它能消除 decode 成本

本轮性能测试的目标不是和所有历史口径做严格横向对齐，
而是先拿到一版对当前 `0428 phase4 http` 场景有代表性的性能基线。

### 测试口径

本轮采用的是 `0428 perf_probe` 口径，而不是单独的
`api-server-profiler` header 口径。

选择这个口径的原因：

1. 当前 `0428 phase4` 主服务已经带了 `VLLM_ASCEND_PERF_PROBE=1`
2. 这套链路可以一次性拿到：
   - `TTFT / TPOT / E2E`
   - `api_server` 热点
   - `engine_core` 热点
   - `tp_worker` 热点
3. 更贴合当前 `0428 phase4 patch` 的真实运行形态

执行方式：

1. 保留现有 `0428 phase4` 服务
2. 保留本地 `9000` 静态 HTTP 服务
3. 将性能图片数据通过静态根映射到 `http://127.0.0.1:9000/...`
4. 把 benchmark payload 改写成 HTTP 输入
5. 运行 `0428/scripts/run_multimodal_baseline.py`
   - `3` 次 warmup
   - `10` 次正式测试
6. 从 `/tmp/vllm_ascend_perf_probe.jsonl` 和结果 JSON 汇总结果

### 结论

1. `phase4 http` 对 `TTFT / TTST / E2E` 的改善非常明显

## 2026-04-29：phase4 可靠性加固方案与 patch 实施

### 背景

在完成 `phase4` 三种 transport 的精度矩阵回归后，当前主问题已经不再是
`http/base64/local_path` 串扰，而是 `phase4 http cache` 作为长期运行能力时，
还缺少一层明确的可靠性治理。

本轮围绕下面三个加固点直接修改 `0428` 内 patch，不触碰外部安装版
`vllm` / `vllm-ascend` 源码：

1. 识别并清理坏缓存
2. 设置缓存大小上限与清退
3. phase4 失败回退可观测

核心修改文件：

- `0428/bundle/vllm_phase2_plugin/patches/phase1.py`

辅助修改：

- `0428/bundle/start_phase4_server.sh`

### 设计目标

#### 1. 坏缓存自愈

目标：

- `phase4` API server 侧命中 cache 后，如果本地缓存文件已经不是可用图片，
  不应该反复命中“毒缓存”
- 应该立即删除对应缓存文件与 meta
- 当前请求明确回退到 stock http 路径
- 同时留下足够清晰的 trace 方便复盘

落点：

- `phase4 http -> materialize -> phase3 local ref` 链路
- 具体在 `phase1.py` 的 `_phase4_http_image_from_url()` 内判断

选择 API server 侧而不是 tp worker 侧的原因：

1. cache 的所有权就在 API server
2. 当前链路本来就需要本地打开图片拿 `width/height`
3. 不把 cache 生命周期管理散到 worker 多 rank 路径

实现语义：

1. cache hit 后继续走本地文件探测
2. 如果本地文件不存在或 `PIL.open()` 失败：
   - 判定为 `cache_invalid`
   - 删除该 `cache_key` 下的图片文件和 `.json`
   - 写 `phase4_http_cache_invalid`
   - 当前请求写 `phase4_http_fallback_stock`
   - fallback 到 stock http 路径

说明：

- 这里不额外引入二次 `verify()` 全量 decode
- 直接复用本来就需要执行的本地图片探测动作
- 因此正常请求几乎没有新增耗时
- 只有命中坏缓存的那次请求会多承担一次清理和 fallback 成本

#### 2. 缓存大小上限与清退

新增环境变量：

- `VLLM_ASCEND_HTTP_CACHE_MAX_GB`

建议语义：

- `<= 0`：不限制缓存总容量
- `> 0`：限制 `phase4 http cache` 目录可占用的总字节数

实现策略：

1. 只在 `cache fill` 成功后触发治理
2. 不在每个请求命中路径上全目录重扫
3. 治理时优先清理：
   - 已过 TTL 的条目
   - 本地文件丢失的条目
4. 如果仍超上限，再按最旧 `downloaded_at` 优先淘汰
5. 当前刚写入的 `cache_key` 不作为第一优先淘汰对象

这样做的目的：

- 避免每个 hit 请求都承担全目录扫描开销
- 把容量治理压到“新增缓存”的时刻触发
- 兼顾 TTL 清理和容量上限治理

#### 3. fallback 可观测

现有问题：

- materialize 失败、坏缓存失效、回退 stock 这些行为之前没有完整的
  reason/stage 观测
- 长期运行里如果 `phase4` 静默回退，运维侧不容易第一时间判断

本轮补充的关键 trace：

- `phase4_http_cache_hit`
- `phase4_http_cache_fill`
- `phase4_http_cache_error`
- `phase4_http_cache_invalid`
- `phase4_http_cache_evict`
- `phase4_http_cache_gc`
- `phase4_http_fallback_stock`

其中 `phase4_http_fallback_stock` 会明确附带：

- `fallback_reason`
- `image_url`
- `canonical_http_url`
- `source_key`
- 必要时补 `error`

### patch 实施点

#### `phase1.py`

新增/调整点：

1. 新增 `_phase4_http_cache_max_bytes()`
   - 解析 `VLLM_ASCEND_HTTP_CACHE_MAX_GB`
2. 新增 cache invalidation/eviction/gc 辅助函数
   - 统一做 `cache_key` 级文件清理
   - 统一记录 trace
3. `cache fill` 成功后触发 `_phase4_prune_http_cache()`
4. 新增 `_phase3_probe_local_image()`
   - 统一返回 `width/height/error`
   - 供本地 ref 以及 bad cache 自愈共同复用
5. `phase4` 命中 cache 后如果本地图片不可用：
   - 删除缓存
   - 记录 `phase4_http_cache_invalid`
   - 记录 `phase4_http_fallback_stock`
   - 回退 stock 路径
6. materialize 失败或本地路径异常时：
   - 统一记录 `phase4_http_fallback_stock`

#### `start_phase4_server.sh`

补充默认 env：

- `VLLM_ASCEND_HTTP_CACHE_MAX_GB="${VLLM_ASCEND_HTTP_CACHE_MAX_GB:-0}"`

这样 phase4 启动入口默认就具备容量治理开关，只是默认关闭上限。

### 当前设计取舍

1. 坏缓存自愈先做成“删除后 fallback”，不做“同请求内自动重拉”

原因：

- 第一版更稳
- 路径更清晰
- 不会把当前请求链路复杂化
- 后续如果确实需要，再单独评估 `invalidate -> re-materialize once`

2. cache gc 采用 fill 后触发，而不是每次 hit 触发

原因：

- 命中路径要尽量轻
- 容量增长只会发生在 fill 时
- 长期治理场景里，fill 时顺手做一次更合适

3. eviction 尽量非阻塞跳过 busy key

原因：

- 不和正在下载或正在命中的 key 硬抢锁
- 避免 cache gc 反过来成为请求路径上的大阻塞点

### 后续建议验证项

建议按下面顺序验证：

1. 坏缓存自愈
   - 先让某个 URL 正常 fill
   - 手工改坏缓存文件内容
   - 再次请求同 URL
   - 预期：
     - 出现 `phase4_http_cache_invalid`
     - 出现 `phase4_http_fallback_stock`
     - 缓存文件与 meta 被删除

2. 容量上限
   - 设置 `VLLM_ASCEND_HTTP_CACHE_MAX_GB` 为较小值
   - 连续请求多个不同 URL
   - 预期：
     - `phase4_http_cache_gc` 有记录
     - 超限后出现 `phase4_http_cache_evict`
     - 旧条目逐步被清理

3. materialize 失败可观测
   - 构造 404 或超时 URL
   - 预期：
     - `phase4_http_cache_error`
     - `phase4_http_fallback_stock`
     - `fallback_reason=materialize_failed`

### 结论

这轮 patch 的目标不是继续榨性能，而是让 `phase4 http cache` 更接近一个可以长期跑的
工程化能力：

1. 坏缓存不再长期复用
2. 缓存目录开始具备上限治理能力
3. `phase4` 的失效与回退有了更清楚的可观测信号

这三点都限定在 `0428` 仓库内实现，不依赖修改外部 `vllm` / `vllm-ascend`
安装源码。

到本轮记录为止，可以把 `phase4` 的状态更新为：

1. `http` 已不仅是“功能可用”，而且已经完成：
   - `L0`
   - `L0.5`
   - `MME`
   的正式回归
2. `base64` 也已经在同一 `phase4` 服务上完成：
   - `L0`
   - `L0.5`
   - `MME`
   回归
3. 当前后续默认优先级仍然不变：
   - 首先继续定位和优化 `L0.5`
   - 其次再做更细粒度的精度差异分析

## 2026-04-29：phase4 可靠性加固方案

### 背景

到本轮 `phase4` 三种 transport 精度矩阵回归为止，可以确认：

1. `phase4 http` 主能力已经成立
2. 历史上的 transport 串扰问题本轮未复现
3. 当前主要精度问题集中在 `L0.5` 多图能力本身，而不是 `http` 主链不稳定

但从 patch 当前实现逻辑看，`phase4` 仍然有三类工程可靠性风险需要主动加固：

1. 坏缓存缺少自愈
2. 缓存目录缺少容量治理
3. `phase4` 失效后的 fallback 可观测性不足

这些问题不会立即让功能不可用，但在长期运行、缓存目录持续增长、
上游图片偶发异常、或者某些 URL 内容发生变化时，会逐步放大为稳定性问题。

### 目标

本轮可靠性加固限定在：

- 只修改 `0428/` 目录下 patch 与启动脚本
- 不修改 `vllm` / `vllm-ascend` 源码
- 不改变 `phase4` 的基本能力定义：
  - `http` transport 身份仍然保持为 `http`
  - worker 继续复用 `phase3 direct encode`
  - materialize 失败时仍允许回退 stock 路径

### 加固点 1：识别并清理坏缓存

#### 问题

当前 `phase4` cache hit 的 freshness 主要基于：

- `local_path` 文件存在
- `downloaded_at` 未超过 TTL

但这还不够，因为存在下面几种坏缓存场景：

1. 远端返回 `200`，但内容不是有效图片
   - 例如 HTML 错误页、代理页、损坏二进制
2. 缓存文件落盘后被外部破坏
3. 缓存文件存在，但 `PIL` 已无法正常打开

当前逻辑下，这类坏缓存会：

1. 先被命中为 `phase4_http_cache_hit`
2. 然后在本地图片转 `phase3 local ref` 时失败
3. 最终请求回退到 stock 路径

但坏缓存本身不会被删掉，后续同 URL 请求还会反复命中这份坏缓存。

#### 方案

坏缓存自愈放在 `api server` 侧，而不是 `tp worker`。

原因：

1. `phase4` cache 的所有权在 `api server`
   - URL 下载
   - meta 写入
   - TTL 判断
   都在这里
2. `api server` 当前本来就要在命中缓存后打开本地文件获取宽高
   - 复用这个动作判断缓存是否可用，额外开销最小
3. 如果放到 `tp worker`
   - 会更晚发现问题
   - 会让多个 rank 重复判断
   - 会把 cache 生命周期治理逻辑散到执行侧

具体策略：

1. `phase4 http` 命中 cache 后，继续走本地 ref 构造
2. 如果本地文件无法被 `_phase3_local_image_from_path()` 正常打开：
   - 立即判定为坏缓存
   - 删除缓存图片文件
   - 删除对应 meta 文件
   - 记录 `phase4_http_cache_invalid`
3. 然后本次请求不再信任这份缓存：
   - 第一版优先回退 stock 路径
   - 不在同一次请求内强行重拉，避免把请求路径复杂度抬高过多

#### 预期效果

1. 坏缓存不再长期滞留并反复命中
2. 同一个 URL 最多只会在第一次发现坏缓存时触发一次异常回退
3. 后续请求可以重新 materialize 出一份健康缓存

### 加固点 2：缓存上限与清退

#### 问题

当前 `phase4` 只有 TTL 语义，但没有真正的目录治理：

1. 过期文件不会主动删除
2. 没有总容量上限
3. `.json` / `.lock` / 图片文件会持续积累
4. 长期运行后可能把 cache 目录甚至 `/tmp` 打满

这类问题短测不明显，但在线上长期运行下是典型的可靠性风险。

#### 方案

新增环境变量：

- `VLLM_ASCEND_HTTP_CACHE_MAX_GB`

建议语义：

1. `<= 0`
   - 不限制总容量
2. `> 0`
   - 允许 `phase4 http cache dir` 使用的总容量上限，单位为 `GB`

治理策略：

1. 不在每个请求上做全目录重扫
   - 避免把治理逻辑变成常规请求热点
2. 只在 `cache fill` 成功后触发一次轻量治理
3. 治理顺序优先：
   - 先清理 TTL 已过期项
   - 再在仍然超限时按最老项优先淘汰
4. 清理时同步处理：
   - 图片文件
   - meta 文件
   - 孤儿 lock 文件

#### 预期效果

1. `phase4` 可以长期运行而不依赖人工定期清缓存
2. cache 目录大小可控
3. 老旧、过期、长期不命中的缓存能被逐步回收

### 加固点 3：phase4 失败回退可观测

#### 问题

当前 materialize 失败时，请求仍可回退 stock 路径，这保证了可用性，
但缺少强可观测信号，容易出现下面现象：

1. `phase4` 已经失效，但外部只看到请求还能成功
2. 性能悄悄回退到 stock `http` 链路
3. 排障时必须翻 trace，无法快速判断：
   - 是 cache hit
   - 是 cache invalid
   - 还是 materialize/network/path 问题

#### 方案

补齐 `phase4` 相关 stage/trace，使下列状态可明确区分：

1. `phase4_http_cache_hit`
2. `phase4_http_cache_fill`
3. `phase4_http_cache_error`
4. `phase4_http_cache_invalid`
5. `phase4_http_cache_evict`
6. `phase4_http_fallback_stock`

其中 `phase4_http_fallback_stock` 至少要记录：

- 原始 `image_url`
- canonical url
- fallback reason
- 触发时阶段
- 是否发生在 cache hit 后

fallback reason 建议至少覆盖：

1. `materialize_error`
2. `cache_invalid`
3. `local_ref_build_failed`
4. `non_http_transport`

#### 预期效果

1. 可以快速判断请求到底有没有真正用上 `phase4`
2. 可以区分“phase4 正常命中”和“phase4 已经 silently fallback”
3. 后续无论做性能分析还是故障排查，都更容易建立稳定口径

### 实施顺序

这三项加固默认按下面顺序落地：

1. 先补 fallback / invalid / eviction 可观测
2. 再做坏缓存自愈
3. 最后补容量治理

原因：

1. 先把现场打清楚，便于验证每一类分支是否真实触发

本次验证说明，`phase4` 的三类可靠性加固点在 `tp4` 路径下均已生效。其中缓存容量限制不是只打出 GC 打点，而是已经发生了真实的容量清退。

### 1. 坏缓存识别与自愈

- 结论：通过
- 行为：命中损坏缓存后，服务侧先识别并打出 `phase4_http_cache_invalid`，随后走 `phase4_http_fallback_stock`，原因是 `cache_invalid_local_ref`，最后重新回填缓存。
- 关键证据：
- `/tmp/vllm_ascend_mm_file_map.jsonl:22` 出现 `phase4_http_cache_invalid`
- `/tmp/vllm_ascend_mm_file_map.jsonl:23` 出现 `phase4_http_fallback_stock`，`fallback_reason=cache_invalid_local_ref`
- `/tmp/vllm_ascend_mm_file_map.jsonl:24` 出现重新回填记录

这说明坏缓存自愈链路已经串通：识别坏缓存 -> 回退 stock 取图 -> 恢复缓存。

### 2. 缓存上限与容量清退

- 结论：通过
- 配置：`VLLM_ASCEND_HTTP_CACHE_MAX_GB=0.0001`
- 行为：服务启动后，在请求过程中触发缓存容量检查，随后产生批量 `phase4_http_cache_evict`，原因均为 `capacity_limit`。
- 关键证据：
- `/tmp/vllm_ascend_mm_file_map.jsonl:4573` 出现 `phase4_http_cache_gc`
- 同条记录包含：
- `capacity_removed=4548`
- `initial_total_bytes=149684852`
- `max_bytes=107374`
- `remaining_total_bytes=103278`
- `/tmp/vllm_ascend_mm_file_map.jsonl:25` 起连续出现大量 `phase4_http_cache_evict`

这次验证与上一轮不同。上一轮误以 `VLLM_ASCEND_HTTP_CACHE_MAX_GB=0` 启动，只能证明 GC 路径被调用，不能证明容量限制真正成立；本轮在非零上限下确认了真实 eviction，因此可以判定缓存上限和清退逻辑已经可用。

### 3. phase4 失败回退可观测

- 结论：通过
- 场景：请求缺失 HTTP 资源 `missing-does-not-exist.jpg`
- 行为：trace 中明确记录 `phase4_http_fallback_stock`，原因是 `materialize_failed`；服务侧请求失败也对外可见，满足“失败回退可观测”的目标。
- 关键证据：
- `/tmp/vllm_ascend_mm_file_map.jsonl:4658` 出现 `phase4_http_fallback_stock`
