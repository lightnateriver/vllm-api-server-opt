## 01 项目范围与目标
# 项目述求

## 背景

本项目面向 `Qwen3-VL / Qwen3.5-VL` 类多模态服务场景，重点是降低
API server 在本地多模态输入下的 CPU 侧负担。

典型目标负载：

- 文本：约 `10k` token
- 图像：`40` 张图片
- 部署：`TP4/TP8` + `VIT DP`

原始链路里，API server 会承担：

- 本地图像读取
- PIL decode
- HF processor 图像预处理
- multimodal hash
- 图像相关 shm copy

这些逻辑容易成为 TTFT 和端到端耗时的瓶颈。

## 当前目标

当前版本的交付目标已经从“探索多条 phase3 变体”收敛为：

- 保留 `phase0 ~ phase3` 分阶段验证能力
- 将 `phase3 direct encode` 固化为唯一继续演进的 `phase3` 主方案
- 删除 `phase3-local-only / local-plus` 这类错误或过时实验路径的接手入口
- 明确记录当前已支持：
  - `local_path`
  - `http`

## 核心诉求

1. 不修改原始安装版 `vllm` / `vllm-ascend`
2. 统一通过插件注册和运行期 patch 生效
3. phase 行为由环境变量控制，便于回退
4. API server 尽量只保留调度和轻量请求编排语义
5. worker 承担更多图像处理与 multimodal encode 工作
6. 保留完整的部署、精度验证和性能分析路径

## 当前阶段结论

- `phase3 direct encode` 已经完成主链路落地
- `local_path` 输入已经稳定支持
- `http` 输入已经打通
- 视频请求在 `phase3` 下已通过 patch 修复为稳定路径
- 当前主要待继续优化的是多图精度，而不是服务可用性

## 02 总体设计
# 总体设计

## 交付边界

这套交付的边界是：

- 不修改 site-packages 中的 `vllm` / `vllm-ascend`
- 不要求重新打 wheel 或重新安装框架
- 所有行为变化都来自插件注册和运行期 patch
- 所有 phase 都由环境变量控制，方便逐阶段验证和回退

## 设计分层

### 1. 注册层

利用 vLLM 的 general plugin 入口，让原始
`python -m vllm.entrypoints.openai.api_server`
在启动时自动执行本目录里的插件注册函数。

当前交付通过下面两个文件完成插件发现：

- `bundle/vllm_phase2_plugin-0.0.1.dist-info/entry_points.txt`
- `bundle/vllm_phase2_plugin/register.py`

其中 entry point 名称是 `phase2_local_plugin`，启动脚本会设置：

```bash
export VLLM_PLUGINS=phase2_local_plugin,ascend
```

### 2. patch 层

插件入口会根据 `VLLM_ASCEND_API_OPT_PHASE` 决定是否安装 patch：

- `phase1`
  - 本地图像稳定 UUID/hash
- `phase2`
  - `image_url` 对应的本地路径透传到 engine core / worker
- `phase3`
  - `phase3 direct encode`
  - API server 不再承担本地图像主处理工作
  - worker 承担 multimodal 读取、处理与 encode 主路径
- `perf`
  - API server / engine core / tp worker 的统一打点

当前实现位于：

- `bundle/vllm_phase2_plugin/common/`
- `bundle/vllm_phase2_plugin/patches/`
- `bundle/vllm_phase2_plugin/probes/`

### 3. phase3 direct encode 主方案

当前 `phase3` 的唯一主方案是 `phase3 direct encode`。

目标是把 API server 的重型 multimodal 工作下沉到 worker，使 API 侧尽量只保留：

- 请求解析
- tokenizer
- 调度与 cache 语义

worker 负责：

- 本地路径透传后的 multimodal 数据读取
- HF processor 图像预处理
- direct encode 路径下的本 rank multimodal encode
- 必要时对不适合 direct encode 的模态执行稳定 fallback

### 4. 输入支持边界

当前版本在 `phase3 direct encode` 下明确支持：

- `local_path`
- `http`

说明：

- `local_path` 是当前最主要、最稳定的优化目标
- `http` 已支持，但它的性能口径应和 `local_path` 分开分析
- 视频输入在当前实现下已通过 patch 修复为稳定功能路径

## 启动层

`bundle/start_phase_server.sh` 是统一启动入口，负责：

1. 设置运行时环境变量
2. 把 `bundle/` prepend 到 `PYTHONPATH`
3. 设置 `VLLM_PLUGINS=phase2_local_plugin,ascend`
4. 保持底层服务仍由原始 `python -m vllm.entrypoints.openai.api_server` 启动

phase 专用脚本只负责设置 phase 环境变量后转调统一入口：

- `start_phase0_server.sh`
- `start_phase1_server.sh`
- `start_phase2_server.sh`
- `start_phase3_server.sh`

当前目录不再提供 `phase3-local-only` 或 `phase3-local-plus` 的推荐启动入口。

## 默认运行时参数

启动脚本默认对齐当前验证环境：

- `HCCL_BUFFSIZE=1024`
- `VLLM_ASCEND_ENABLE_PREFETCH_MLP=1`
- `HCCL_OP_EXPANSION_MODE=AIV`
- `CPU_AFFINITY_CONF=1`
- `VLLM_USE_V1=1`
- `PYTORCH_NPU_ALLOC_CONF=expandable_segments:True`
- `--async-scheduling`
- `--additional-config '{"enable_cpu_binding": true}'`
- `--enforce-eager`
- `--tensor-parallel-size 4`
- `--mm-processor-cache-type shm`
- `--mm-processor-cache-gb 20`
- `--mm-encoder-tp-mode data`
- `--gpu-memory-utilization 0.85`
- `--max-model-len 36864`

这些都可以通过环境变量覆盖。

## 当前已完成状态

当前已经完成的设计目标：

- `phase1/phase2/phase3` 插件化接入
- `phase3 direct encode` 主链路落地
- `local_path` 图片支持
- `local_path` 视频支持
- `http` 输入支持
- `phase3` 视频请求稳定性修复

## 当前仍待继续工作的方向

后续默认继续推进：

1. `phase3 direct encode` 多图精度优化
2. `local_path` / `http` 统一精度回归
3. worker 热点进一步优化

## 03 Phase0~Phase4 分阶段设计与实现
# Phase 设计目标与实现

## phase0

设计目标：

- 保留原始多模态处理链路
- 只增加统一性能打点
- 作为精度和性能基线

实现方案：

- `VLLM_ASCEND_API_OPT_PHASE=0`
- 不启用 phase1/2/3 的行为变更
- 只启用性能 probe patch

链路特点：

- API server 负责本地图像读取
- API server 负责 HF processor 图像预处理
- API server 负责 mm cache / shm copy
- worker 维持原始推理消费方式

## phase1

设计目标：

- 降低本地图像 hash 计算成本
- 避免每次都基于图像内容做重 hash

实现方案：

- `VLLM_ASCEND_API_OPT_PHASE=1`
- 在 `bundle/vllm_phase2_plugin/patches/phase1.py` 中，把本地图像身份切换到稳定 UUID/hash
- UUID 由本地路径和文件修改时间派生

链路特点：

- 除 hash 行为外，其余链路仍基本保持 phase0 语义
- 主要观察 `ProcessorInputs.get_mm_hashes` 和 phase1 repeat-hit 测试结果

## phase2

设计目标：

- 把 `image_url` 对应的本地路径透传到 engine core / worker
- 验证 worker 侧具备按 vit-DP 分工读取图片的能力
- 在不改变 API server 主处理语义的前提下先打通正确性链路

实现方案：

- `VLLM_ASCEND_API_OPT_PHASE=2`
- API server 继续保留原多模态处理主路径
- 附加透传本地图片路径信息到 engine core / worker
- worker 按 vit-DP 负载切片，只读取自己负责的图片子集

链路特点：

- 这个阶段以“链路正确性”和“透传打通”为主
- 不以最终性能最优为目标

## phase3

设计目标：

- 真正把 API server 的图像读取与图像处理下沉到 worker
- 让 API server 尽量只保留请求编排、tokenizer、cache 语义
- 固化 `phase3 direct encode` 作为唯一继续演进的 phase3 主方案

实现方案：

- `VLLM_ASCEND_API_OPT_PHASE=3`
- API server 不再做本地图像主读取
- API server 不再做本地图像 HF 预处理主路径
- worker 负责：
  - 按 vit-DP 切分 multimodal 数据
  - 读取本地图片
  - 执行 HF preprocess
  - direct encode 主路径
  - 对当前不适合 direct encode 的模态执行稳定 fallback

链路特点：

- API 热点应明显下降
- 热点会迁移到 tp worker
- `phase3 direct encode` 当前已经支持：
  - `local_path`
  - `http`
- 当前主要剩余问题是多图精度，不是服务稳定性

## phase4

设计目标：

- 让 `http` 输入也能获得 `phase3 direct encode` 的收益
- 不修改 `vllm` / `vllm-ascend` 源码
- 仅通过 `0428` patch 增量实现

实现方案：

- `VLLM_ASCEND_API_OPT_PHASE=4`
- API server 先把 `http/https` 图片下载到本地缓存池
- 下载后构造 phase3-style local image ref
- worker 继续复用 `phase3 direct encode`

链路特点：

- transport 身份仍然记录为 `http`
- 但 worker 消费的是缓存后的本地文件路径
- 下载失败时回退到 stock `http` 图片处理路径
- `local_path` / `base64` 逻辑不受影响

## 不再继续维护的旧实验路径

下列历史实验路径不再作为当前目录的推荐方案：

- `phase3-local-only`
- `phase3-local-plus`

原因：

- 它们不再是后续继续开发的主线
- 它们会干扰接手人对当前正确方案的理解
- 当前已经确认 `phase3 direct encode` 才是需要继续打磨的主方案

## 04 API Server 下沉总体方案设计
# API Server 下沉总体方案设计文档

## 1. 文档目的

本文档用于完整描述当前多模态服务优化方案，重点解释：

- 为什么要做 API server 下沉
- `phase0 ~ phase3` 每个阶段分别在解决什么问题
- `phase3 direct encode` 为什么是当前唯一继续演进的主方案
- 当前代码里具体修改了哪些层、哪些参数和哪些数据流
- 当前已经支持哪些输入形式
- 后续接手任务时应该从哪里继续推进

本文档是 `0428/` 目录下最完整的方案说明，适合作为新任务接手时的首要设计参考。

## 2. 背景

### 2.1 业务背景

目标模型为 `Qwen3.5-4B` 多模态服务，典型输入特征为：

- 文本约 `10k` token
- 图片约 `40` 张
- 部署模式以 `tp4`、`--enforce-eager`、`mm shm cache` 为主

原始 vLLM 多模态链路在处理本地图片输入时，API server 会承担大量 CPU 侧工作：

- 本地文件路径解析
- 图片文件读取
- 图片解码
- HF processor 预处理
- 多模态 hash 计算
- multimodal cache / shm 相关处理

当单请求里图片数较多时，API server 会成为 TTFT 和端到端时延的热点区域。

### 2.2 工程约束

本项目始终遵守以下工程约束：

1. 不修改 site-packages 中原始安装版 `vllm` / `vllm-ascend`
2. 不要求重新打 wheel 或二次安装框架
3. 所有行为变化通过插件注册和运行期 patch 实现
4. phase 行为由环境变量切换，便于回退和逐阶段验证

## 3. 设计目标

### 3.1 总体目标

总体目标是逐步把多模态请求中的重型图像处理逻辑从 API server 下沉到 worker，
使 API server 尽量只保留轻量控制面语义：

- 请求解析
- tokenizer
- 请求调度
- cache 语义

同时让 worker 接管：

- 图像读取
- 图像预处理
- multimodal encode 主路径

### 3.2 当前阶段目标

当前 `0428` 版本的目标已经明确收敛为：

1. 保留 `phase0 ~ phase3` 的渐进式验证链
2. 固化 `phase3 direct encode` 为唯一继续演进的 `phase3` 主方案
3. 明确支持：
   - `local_path`
   - `http`
4. 修复历史上 `phase3` 在视频本地输入下的稳定性问题
5. 将剩余问题收敛为多图精度优化，而非服务稳定性问题

### 3.3 非目标

当前版本不再追求：

- 继续维护 `phase3-local-only`
- 继续维护 `phase3-local-plus`
- 在当前目录中保留历史试验分支作为正式入口
- 在没有稳定精度前贸然继续扩展更多并发/性能变体

## 4. 方案演进概览

### 4.1 演进思想

`phase0 ~ phase3` 的设计思路不是一次性推翻原始链路，而是分阶段验证：

1. 先建立基线
2. 再优化 hash
3. 再透传本地路径
4. 最后真正下沉图像主处理链路

### 4.2 Phase 划分

#### phase0

目标：

- 完全保留原始多模态处理主链路
- 只增加统一性能打点
- 作为精度和性能基线

#### phase1

目标：

- 降低本地图片 hash 计算成本
- 避免每次都基于完整图像内容做重 hash

#### phase2

目标：

- 把本地图片路径透传到 engine core / worker
- 验证 worker 侧按 vit-DP 分工读取图片的能力
- 不改变 API server 主图像处理语义，只先打通数据透传和 worker 感知

#### phase3

目标：

- 将 API server 的本地图像主处理链路下沉到 worker
- 让 worker 接管 direct encode 主路径
- 保持对不适合 direct encode 的模态执行稳定 fallback

当前 `phase3` 的唯一主方案就是：

- `phase3 direct encode`

## 5. 当前主方案：phase3 direct encode

## 5.1 方案定义

`phase3 direct encode` 指的是：

- API server 不再承担本地图像主读取与主预处理
- worker 在接收到透传路径和必要元数据后，执行本 rank 需要的 multimodal 处理
- 对支持 direct encode 的路径，worker 自行完成 encode 并回填 encoder cache
- 对当前不适合 direct encode 的模态，比如当前视频路径，执行稳定 fallback

### 5.2 为什么不继续使用 phase3-local-only

历史上的 `phase3-local-only / local-plus` 方案存在两个问题：

1. 容易让接手人误以为它仍然是推荐主线
2. 会把当前真正应该继续维护的 `phase3 direct encode` 主方案和旧实验路径混在一起

因此在 `0428` 中：

- 代码入口已下线
- 启动脚本已删除
- 文档只保留“历史上存在，但已下线”的说明

## 6. 原始链路与修改后链路

### 6.1 原始 phase0 数据流

```text
Client
  |
  v
OpenAI API Server
  |
  |-- parse request
  |-- read local image/video path
  |-- load file / decode image
  |-- run HF multimodal processor
  |-- compute mm hash
  |-- build mm cache / shm payload
  v
Engine Core
  |
  |-- schedule request
  |-- prepare encoder inputs
  v
TP Workers
  |
  |-- consume prebuilt multimodal inputs
  |-- run model forward
  v
Response
```

### 6.2 phase1 数据流

```text
Client
  |
  v
OpenAI API Server
  |
  |-- same as phase0 main path
  |-- replace local image identity with stable UUID/hash
  v
Engine Core
  |
  v
TP Workers
  |
  v
Response
```

变化点：

- 主数据流基本不变
- 只优化本地图片 hash 计算方式

### 6.3 phase2 数据流

```text
Client
  |
  v
OpenAI API Server
  |
  |-- still loads and preprocesses image in main path
  |-- additionally collect local media paths
  |-- attach local paths into request/extra_args
  v
Engine Core
  |
  |-- keep request scheduling
  |-- preserve local path metadata
  v
TP Workers
  |
  |-- see local paths
  |-- validate local shard mapping
  |-- can load local shard for correctness checks
  v
Response
```

变化点：

- 重点是“透传本地路径”
- 不是最终性能形态

### 6.4 phase3 direct encode 数据流

```text
Client
  |
  v
OpenAI API Server
  |
  |-- parse request
  |-- keep request orchestration / tokenizer / cache semantics
  |-- for local_path and supported http path:
  |     do not perform full image preprocess main path
  |     only keep lightweight metadata needed by downstream
  v
Engine Core
  |
  |-- schedule encoder inputs
  |-- pass request state / multimodal metadata to workers
  v
TP Workers
  |
  |-- compute local shard assignment
  |-- load only local images for this rank
  |-- run HF multimodal preprocess on local shard
  |-- direct encode local shard
  |-- all-gather / rebuild original order if needed
  |-- write encoder outputs into encoder cache
  |-- for unsupported modality:
  |     fallback to stock encoder path
  v
Model Forward
  |
  v
Response
```

### 6.5 当前视频路径的数据流

当前视频请求已经修复，但它不是纯 direct encode 主路径，而是：

```text
Video local_path request
  |
  v
Phase3 worker patch detects unsupported / non-image modality
  |
  v
Explicit fallback to stock encoder execution
  |
  v
Stock encoder fills encoder cache
  |
  v
Normal forward continues without cache miss
```

这正是当前版本修复历史 `Encoder cache miss -> 500` 的关键点。

## 05 HTTP 输入 Phase4 优化设计
# HTTP输入 Phase4 优化设计

## 1. 文档目标

本文档描述 `0428/` 目录中新引入的 `phase4` 方案。

`phase4` 的目标不是替换 `phase3 direct encode`，而是补齐一个明确的能力缺口：

- 让 `http` 输入也能获得接近 `local_path + phase3 direct encode` 的收益
- 且不修改 `vllm` / `vllm-ascend` 源码
- 只通过 `0428/bundle/vllm_phase2_plugin` 的运行期 patch 实现

一句话概括：

`phase4 = API server 先把 http 图片下载并缓存到本地，再复用 phase3 direct encode 的 worker 侧本地路径链路。`

---

## 2. 背景与问题定义

### 2.1 phase3 已解决什么

`phase3 direct encode` 已经在 `local_path` 输入下实现了 API server 下沉：

- API server 不再承担本地图像主读取
- API server 不再承担本地图像主预处理
- worker 按 TP/ViT-DP 负责自己分片的图片读取、HF preprocess 和 encode

这条链路已经证明对 `local_path` 是有效的。

### 2.2 phase3 在 http 输入下的局限

在 `phase3` 但还没有 `phase4` 时，`http` 输入虽然“功能可用”，但并不能享受真正的 direct encode 优化收益。

原因是：

1. `http` URL 不是本地路径
2. API patch 无法像 `local_path` 那样直接构造 `_Phase3LocalImageRef`
3. 因此 `phase3_local_mm_ready=False`
4. worker 侧不会进入现有 `phase3 direct encode` 本地路径流程
5. 请求最终会回到 stock 的图片抓取与处理逻辑

这意味着：

- `http` 输入在 `phase3` 下更多是“兼容支持”
- 不是“真正优化后的下沉路径”

### 2.3 本阶段的核心目标

`phase4` 要解决的问题是：

`如何让远端 http 图片请求，在不修改 stock vLLM 源码的前提下，复用 phase3 direct encode 的本地路径优化链路。`

---

## 3. 设计目标

### 3.1 必须满足的目标

1. 不修改 `vllm` / `vllm-ascend` 源码
2. 只改 `0428` 下的 patch、脚本、文档
3. 不影响 `phase0 ~ phase3` 已有行为
4. `phase4` 必须只在 `VLLM_ASCEND_API_OPT_PHASE >= 4` 时生效
5. 远端 `http/https` 输入优先支持
6. 本地静态 `http` 输入自然兼容
7. 复用现有 `phase3 direct encode` worker 主链路
8. 失败时能回落到 stock `http` 抓图逻辑，保证服务可用

### 3.2 非目标

本阶段不做：

1. 不做图像内容 hash 去重
2. 不做跨 transport 的统一内容级缓存
3. 不做视频 http 输入的 phase4 优化
4. 不改 worker 让其直接下载远端 http 资源

---

## 4. 为什么选择“API server 本地缓存池”

我们考虑过两类思路。

### 4.1 方案A：worker 直接下载 http 图片

优点：

- API server 看起来更轻

缺点：

1. 每个 worker/rank 都可能重复下载
2. 下载动作落到 worker，调度、超时、失败重试更难统一控制
3. 同一请求中，多 rank 对同一 URL 的一致性和缓存复用更难收敛
4. 与当前 `phase3` 已有“按本地路径 direct encode”的实现复用度低

### 4.2 方案B：API server 下载到本地缓存池，再当作 local_path 走 phase3

优点：

1. 只下载一次
2. 更容易做 TTL、锁、大小限制、trace
3. 下载完成后天然变成“本地文件”
4. 可直接复用现有 `phase3 direct encode` worker 流程
5. 对 worker 改动最小

缺点：

1. API server 增加一次 URL 到本地文件的 materialize 动作
2. 需要额外缓存目录和生命周期管理

### 4.3 结论

本期选择方案B：

`API server 本地缓存池 + 物化到本地 + 复用 phase3 direct encode`

这是当前改动最小、风险最小、最符合现有代码演进方向的方案。

---

## 5. 总体方案

## 5.1 方案定义

当请求中的图片是 `http/https` URL 且当前 phase 为 `4` 时：

1. API server 识别该输入是 HTTP 图片
2. 先按 canonical URL 计算缓存 key
3. 在本地缓存目录中检查是否存在可复用的本地文件
4. 若命中，则直接得到本地缓存文件路径
5. 若未命中，则由 API server 下载远端图片到缓存目录
6. 下载成功后，构造一个“带本地路径的 phase3 图片引用对象”
7. 下游继续沿用 `phase3 direct encode` 的本地路径透传与 worker encode 流程

关键点：

- transport 身份仍然记录为 `media_mode=http`
- 但 `_phase2_local_path` 指向本地缓存文件
- 所以下游 worker 可以把它当成本地图片读取

## 5.2 目标数据流

### phase3 下的 http 原链路

```text
Client
  |
  v
API Server
  |
  |-- 识别到 http URL
  |-- 无法构造 local_path phase3 ref
  |-- 继续走 stock fetch/decode
  v
Engine Core / Worker
  |
  |-- phase3_local_mm_ready = false
  |-- 不进入 direct encode 本地路径主链
  v
Response
```

### phase4 下的 http 新链路

```text
Client
  |
  v
API Server
  |
  |-- 识别到 http URL
  |-- canonicalize URL
  |-- 查询本地 HTTP cache pool
  |   |-- hit  -> 直接拿到 local cached file
  |   |-- miss -> 下载远端图片到本地缓存
  |
  |-- 构造 phase3-style local image ref
  |   media_mode = http
  |   local_path = /tmp/vllm_ascend_http_cache/<sha1>.jpg
  v
Renderer / Engine Input
  |
  |-- phase3_local_mm_ready = true
  |-- phase2_local_mm_paths 透传缓存后的 local_path
  v
TP Worker
  |
  |-- 复用 phase3 direct encode
  |-- 读取 cached local file
  |-- HF preprocess
  |-- direct encode
  |-- 回填 encoder cache
  v
Response
```

---

## 6. 核心设计细节

## 6.1 缓存 key

`phase4` 不按图像内容计算 hash，而按 URL 身份计算。

当前 key 规则：

```text
cache_key = sha1(canonical_http_url)
```

其中 `canonical_http_url` 规则：

- 只接受 `http` / `https`
- 去掉 fragment
- 保留 path / query

设计原因：

1. 计算便宜
2. 不需要先读取整图内容
3. 与 transport 身份天然绑定
4. 满足本阶段“远端 URL 复用”的主要目标

## 6.2 transport 身份与本地路径并存

这是 `phase4` 最关键的设计点。

缓存后的图片虽然已经落盘为本地文件，但它的逻辑来源仍然是 `http`。

因此 patch 中同时保留两类信息：

- `media_mode = http`
- `local_path = /tmp/.../<cache_key>.<suffix>`

这意味着：

1. 下游 direct encode 可以复用本地文件
2. 调试和 trace 里仍然能看出它来自 HTTP 输入
3. 不会把它错误伪装成真正的用户 `local_path`

## 6.3 API 侧缓存池目录

默认目录：

```text
/tmp/vllm_ascend_http_cache
```

可通过环境变量覆盖：

```bash
export VLLM_ASCEND_HTTP_CACHE_DIR=/path/to/cache_dir
```

缓存池内容包括：

1. 图片文件本体
2. 同 key 的 JSON meta 文件
3. 同 key 的 lock 文件

## 6.4 TTL

默认 TTL：

```text
86400 秒
```

可通过环境变量覆盖：

```bash
export VLLM_ASCEND_HTTP_CACHE_TTL_S=86400
```

语义：

- TTL 内且本地文件存在，认为 cache hit
- TTL 超过后重新下载覆盖
- 如果 TTL < 0，则视为永久有效，直到文件被人工清理

## 6.5 文件锁

为了避免并发请求对同一个 URL 同时下载，`phase4` 使用基于文件的排它锁：

```text
<cache_key>.lock
```

流程：

1. 进入 materialize 流程
2. 打开 lock 文件
3. `fcntl.flock(..., LOCK_EX)`
4. 二次检查 meta 是否已被其它进程填充
5. 命中则直接复用
6. 未命中才下载

这样可以避免：

- 重复下载
- 半成品文件被其它请求抢读

## 6.6 下载限制

当前实现提供以下保护项：

### 超时

```bash
export VLLM_ASCEND_HTTP_TIMEOUT_S=30
```

### 最大文件大小

默认 `64MB`：

```bash
export VLLM_ASCEND_HTTP_MAX_FILE_BYTES=67108864
```

### 分块大小

默认 `1MB`：

```bash
export VLLM_ASCEND_HTTP_CHUNK_BYTES=1048576
```

### User-Agent

```bash
export VLLM_ASCEND_HTTP_USER_AGENT=vllm-ascend-phase4-http-cache/1.0
```

## 8. 兼容性与边界

## 8.1 对 phase0~phase3 的隔离

`phase4` 只在下面条件同时成立时生效：

1. `VLLM_ASCEND_API_OPT_PHASE >= 4`
2. 当前输入是 `http/https` 图片 URL
3. materialize 成功

否则行为保持为：

- phase0~phase3 完全不变
- phase4 下若 materialize 失败，则回退 stock http 图片抓取逻辑

## 8.2 为什么 phase4 不影响 local_path

Phase4 不改 `local_path` 的主链路。

优先级是：

1. 先尝试 `local_path -> phase3 direct encode`
2. 只有不是本地路径且 phase4 开启时，才尝试 `http -> local cache -> phase3 direct encode`

## 8.3 为什么 phase4 不影响 base64

`base64` 输入仍保持原有 transport identity 规则，不经过 phase4。

因为：

- `phase4` 的问题域只针对 `http/https`
- base64 没有“远端 URL 可复用下载”的问题

---

## 9. 失败回退策略

只要下列任一条件不满足，就不强行走 Phase4：

1. URL 不是 `http/https`
2. 本地缓存目录创建失败
3. 下载超时
4. 返回非预期响应
5. 文件大小超过限制
6. 下载后的文件无法被 PIL 正常识别为图片

此时统一回退到 stock 行为：

- 继续由原始 `vllm` 图片抓取逻辑处理

这保证了：

- `phase4` 是“优化增强”
- 不是“功能替代”

---

## 10. 方案收益

在理想命中场景下，`phase4` 可以带来以下收益：

1. 远端 HTTP 图片只需下载一次
2. 重复请求可直接复用本地缓存文件
3. 下载完成后，下游进入与 `local_path` 一致的 direct encode worker 主链
4. API server 不再为每个请求重复承担完整的 stock HTTP 图片处理路径

对于本地静态 HTTP 服务场景，收益会更接近 `local_path`。

对于真实远端 HTTP 服务场景，Phase4 至少能保证：

- 首次请求的“下载成本”和“worker direct encode 成本”解耦
- 后续同 URL 请求可复用本地缓存

---

## 11. 风险与注意事项

1. `phase4` 无法消除第一次请求的远端下载成本
2. 如果远端资源内容变化但 URL 不变，在 TTL 期间会命中旧缓存
3. 缓存目录需要可写空间
4. 如果远端图片很多且 URL 离散，缓存目录会持续增长，需要后续补后台清理策略
5. 当前实现主要针对图片，不扩展到视频

## 1. 项目整体说明

### 1.1 项目名称 / 用途

项目可概括为：

`0428 Phase0~3 / Phase3 Direct Encode API Server 下沉交付工程`

用途是为 `Qwen3.5-4B` 多模态服务提供一套**不修改原始安装版 `vllm` / `vllm-ascend`** 的运行期增强方案，目标是逐步把原本压在 API server 上的多模态重处理逻辑下沉到 worker 侧。

这个目录不是一个独立重写的服务框架，而是一个**围绕 stock vLLM OpenAI API server 的插件化 patch 工程**。

它承担三类职责：

1. 交付可运行的 phase0 ~ phase3 启动方案。
2. 交付 `phase3 direct encode` 的当前主线实现。
3. 交付完整的精度、性能、对比、回归工具链。

### 1.2 基于什么框架

底座框架仍然是：

- `vLLM`
- `vllm-ascend`

真正启动的仍然是：

`python -m vllm.entrypoints.openai.api_server`

`0428/` 并没有替换这个入口，而是在它启动前通过 `vLLM general plugin` 机制完成 patch 注册。

从目录和代码职责看，这套工程可以分成 5 层。

```text
register()
  -> apply_phase1_patch()
  -> if phase >= 2:
       apply_phase23_patches(enable_phase3 = phase >= 3)
  -> apply_perf_patches()
```

#### 1.4.3 请求处理总览

当前代码下，一个多模态请求会经过如下层次：

```text
Client

    -> renderer
    -> OpenAI request -> sampling params
    -> engine input processor
    -> engine core scheduler
    -> TP worker
      -> phase2/phase3 worker-side multimodal path
      -> stock model execute / direct encode / fallback
  -> stream response
```

## 2. 原始设计目标

这一部分不是引用历史聊天，而是**根据当前代码反推最初想做什么**。

### 2.1 原始需求

从本文档前面的项目范围、总体设计、API Server 下沉方案章节以及 patch 结构反推，原始需求是：

1. 针对多模态大请求场景降低 API server 热点。
2. 保持 stock `vLLM` / `vllm-ascend` 不变。
3. 通过逐阶段 phase 演进，先建立基线，再逐步下沉图像处理。
4. 让 worker 承担更多 multimodal 读取、预处理和 encode 工作。
5. 保留可回退、可对比、可验证的工程形态。

### 2.2 业务场景假设

代码和文档里反复出现的目标负载是：

- 文本约 `10k` token
- 图片约 `40` 张
- 部署常态是 `TP4`
- `--enforce-eager`
- `mm shm cache`
- `mm encoder tp mode=data`

这说明原始方案不是面向“单张图 demo”，而是面向**高多图、高上下文、需要关注 TTFT/E2E 的真实服务场景**。

### 2.3 原始痛点

根据 docs 与 patch 命名，原始痛点主要是 API server 承担了太多 CPU 侧工作：

- 本地文件路径解析
- 图片读取
- 图片 decode
- HF multimodal processor 预处理
- multimodal hash 计算
- shm 相关 copy / cache 处理

这些逻辑在图片多、token 长时会成为 API server 热点。

### 2.4 原始预期能力

从 phase 划分可以推断最初预期能力是：

1. `phase0`
   - 作为精度与性能基线
2. `phase1`
   - 优化本地图像 hash 成本
3. `phase2`
   - 把本地路径透传到底层
4. `phase3`
   - 真正让 worker 接管 direct encode 主路径

### 2.5 原始预期架构

最原始的演进式架构可以反推为：

```text
phase0: 不动主链路，只做观察
phase1: 先降低 hash 成本
phase2: 先把 local path 透传到 worker
phase3: 再让 worker 直接做图像处理与 encode
```

### 2.6 每个 phase 的原始设计目标

#### 2.6.1 phase0

原始目标：

- 保持 stock 行为
- 加统一性能探针
- 建基线

原始主流程字符图：

```text
Client
  -> API server
    -> 读图 / decode / HF preprocess / mm hash / shm copy
  -> engine core
  -> tp worker
  -> response
```

#### 2.6.2 phase1

原始目标：

- 不动多模态主链路
- 只先优化本地图像 identity / hash

原始主流程字符图：

```text
Client
  -> API server
    -> 本地图片不再依赖昂贵内容 hash
    -> 改用稳定 UUID / 文件身份
  -> 其余链路维持 phase0
```

#### 2.6.3 phase2

原始目标：

- 打通“路径透传”
- worker 能感知 local path
- 验证按 vit-DP 分工读取本地图的正确性

原始主流程字符图：

```text
Client
  -> API server
    -> 正常做原始多模态处理
    -> 额外采集 local path 元数据
  -> engine core
    -> 保留 local path 到 request state
  -> tp worker
    -> 按 local path 读取自己负责的图片子集
```

#### 2.6.4 phase3

原始目标：

- 真正把图像主处理链路下沉到 worker
- API server 只保留轻量编排语义

原始主流程字符图：

```text
Client
  -> API server
    -> 仅保留 request parse / tokenizer / scheduling 相关语义
    -> 不再承担本地图像主预处理
  -> engine core
    -> 继续调度 mm encoder inputs
  -> tp worker
    -> load image
    -> hf preprocess
    -> direct encode
    -> 写回 encoder cache
```

### 2.7 原始方案中可能存在的分叉

从 `0427` 遗留文件名可推断，原始 phase3 并不只一个分支，还出现过：

- `phase3-local-only`
- `phase3-local-plus`

这说明最初一段时间里 phase3 方案并未收敛，可能存在多条实验路径并行探索。到了 `0428`，这件事已经被明确收敛：**只保留 `phase3 direct encode` 主线**。

## 3. 最终实际实现方案

这一部分完全基于当前 `0428` 代码，不讨论设想，只讨论真实落地。

### 3.1 核心模块结构

当前代码最终形成了一个“外部插件 + 运行期 monkey patch”的实现体系。

#### 3.1.1 入口发现

文件：

- `bundle/vllm_phase2_plugin-0.0.1.dist-info/entry_points.txt`

内容：

```text
[vllm.general_plugins]
phase2_local_plugin = vllm_phase2_plugin:register
```

这表示 vLLM 会在 general plugin 阶段调用：

`vllm_phase2_plugin.register`

#### 3.1.2 插件入口

文件：

- `bundle/vllm_phase2_plugin/register.py`

逻辑：

```python
def register():
    apply_phase1_patch()
    if phase_at_least(2):
        apply_phase23_patches(enable_phase3=phase_at_least(3))
    apply_perf_patches()
```

结论：

- phase1 patch 是通用前置 patch
- phase2/3 patch 只在 `phase >= 2` 时叠加
- perf patch 始终可启用

### 3.2 phase 选择与配置加载

#### 3.2.1 phase 读取

文件：

- `common/phase.py`

核心函数：

- `phase_value()`
- `phase_at_least(target)`
- `env_flag(name, default=False)`

行为：

- 从 `VLLM_ASCEND_API_OPT_PHASE` 读取 phase 值
- 支持数字字符串
- 支持形如 `phase3`
- 支持布尔风格字符串映射到 phase1

#### 3.2.2 启动配置加载

文件：

- `bundle/start_phase_server.sh`
- `scripts/launch_registered_server.py`

配置加载方式是**环境变量优先**。

主要参数包括：

- `MODEL_DIR`
- `HOST`
- `PORT`
- `TENSOR_PARALLEL_SIZE`
- `MM_PROCESSOR_CACHE_TYPE`
- `MM_PROCESSOR_CACHE_GB`

- `MAX_NUM_BATCHED_TOKENS`
- `ALLOWED_LOCAL_MEDIA_PATH`

此外还会设置运行期 trace/probe 环境变量：

#### 3.2.3 启动器最终传给 stock vLLM 的参数

### 3.3 核心模块与关键类 / 函数

#### 3.3.1 `patches/phase1.py`

这是 API 入口侧最重要的 patch 文件，承担 4 类职责。

##### A. 稳定 local file UUID

关键函数：

- `stable_local_file_uuid(filepath: Path) -> uuid.UUID`

逻辑：

- 基于 `realpath + st_mtime_ns + st_size`
- 计算 md5
- 转成 UUID

用途：

- 避免按图像内容本体做重 hash
- 为本地图片提供稳定身份

##### B. transport/source identity 建模

关键函数：

- `_resolve_image_source_info(parser, image_url, uuid_str)`
- `_resolve_phase3_local_source_info(image_url)`

支持的 source mode：

- `local_path`
- `http`
- `base64`
- `unknown`

规则：

- `local_path`
  - key = `local_path:{realpath}|{mtime_ns}|{size}`
- `http`
  - key = `http:{canonical_url}`
- `base64`
  - key = `base64:req:{request_scope}:image:{idx}`

这是 `0428` 当前非常关键的实现点，因为它显式把 transport mode 纳入 identity。

##### C. phase3 API 轻量图像引用

关键类：

- `_Phase3LocalImageRef`

字段：

- `_phase2_local_path`
- `_phase2_media_mode`
- `_phase2_media_uuid`
- `_phase2_request_scope_key`
- `_phase2_source_key`
- `_phase3_width`
- `_phase3_height`

作用：

- 在 phase3 中，API server 不再立即把本地图读成完整图像数据
- 只构造一个轻量 reference，记录：
  - 本地路径
  - source metadata
  - 图像宽高

##### D. 打 patch 的具体位置

`apply_phase1_patch()` 改写了以下 stock 函数：

- `ImageMediaIO.load_file`
- `MultiModalContentParser.parse_image`
- `AsyncMultiModalContentParser._image_with_uuid_async`
- `MediaConnector.fetch_image`
- `MediaConnector.fetch_image_async`
- `InputPreprocessor._process_text`
- `InputPreprocessor._process_tokens`

这 7 个改写点意味着 phase1/phase3 的第一落点，实际上发生在：

- 图片 URL 解析
- 本地图片载入
- 异步 fetch
- request preprocess

#### 3.3.2 `patches/phase2.py`

这是整套方案真正承上启下的 patch 文件。

它覆盖了 5 个关键层面。

##### A. Renderer patch

函数：

- `patch_phase2_hf_renderer()`

改写：

- `HfRenderer.render_messages`
- `HfRenderer.render_messages_async`
- `BaseRenderer._process_multimodal`
- `BaseRenderer._process_tokens`

作用：

1. 从 `multi_modal_data` 中提取：
   - `phase2_local_mm_paths`
   - `phase2_image_source_metadata`
   - `phase3_local_mm_ready`
2. 在 phase3 + 全本地图片条件下，构造 `grid-only mm_data`
3. 把这些元数据继续塞回 prompt / inputs

这里的核心策略是：

- phase2：路径透传，不改主处理语义
- phase3：对 local_path 主链路可切换到 `build_phase3_mm_data()`

##### B. OpenAI chat request patch

函数：

- `patch_phase2_openai_chat()`

改写：

- `OpenAIServingChat.render_chat_request`
- `ChatCompletionRequest.to_sampling_params`

作用：

- 因为一个 chat request 可能渲染出多个 engine prompt
- 所以代码为每个 prompt 建了队列：
  - `_phase2_local_mm_paths_queue`
  - `_phase3_local_mm_ready_queue`
  - `_phase2_image_source_metadata_queue`
- 在 `to_sampling_params()` 时逐个出队，合并进 `vllm_xargs`

这是 phase2/3 把 API 侧元数据稳定带入 engine request 的关键桥梁。

##### C. Input processor patch

函数：

- `patch_phase2_input_processor()`

改写：

- `InputProcessor.process_inputs`

作用：

- 把 prompt 里带的：
  - `phase2_local_mm_paths`
  - `phase2_image_source_metadata`
  - `phase3_local_mm_ready`
 继续写入 `request.sampling_params.extra_args`

这样 worker 侧的 `req_state` 最终就可以从 `sampling_params.extra_args` 里把 metadata 取出来。

##### D. Qwen parser patch

函数：

- `patch_phase3_qwen_parser()`

改写：

- `Qwen2VLMultiModalDataParser._parse_image_data`

新增内部类：

- `_Phase3GridItems`

作用：

- 在 phase3 下，如果看到的是只含 `image_grid_thw` 而不含 `image_embeds` 的数据结构
- 就把它识别成合法的 image modality items

这一步是 phase3 grid-only API 侧策略能够接入 Qwen parser 的关键点。

##### E. Worker patch

函数：

- `patch_phase2_worker_validation()`

改写：

- `GPUModelRunner._batch_mm_inputs_from_scheduler`
- `GPUModelRunner._execute_mm_encoder`

这是当前整套方案的核心执行落点。

#### 3.3.3 `common/mm.py`

这个文件提供了 worker 与 renderer 的共享工具。

关键职责有 6 类：

1. JSONL trace 写入：
   - `append_jsonl()`
2. tensor / mm item 对比：
   - `tensor_equal()`
   - `summarize_mm_item()`
3. local path 标准化：
   - `normalize_local_mm_paths()`
   - `extract_local_mm_paths_from_mm_data()`
   - `extract_image_paths_for_request()`
4. source metadata 标准化：
   - `normalize_image_source_metadata()`
   - `extract_image_source_metadata_from_mm_data()`
   - `extract_image_source_metadata_for_request()`
5. phase3 API grid-only 构造：
   - `build_phase3_mm_data()`
6. phase3 worker 全量 item 重建辅助：
   - `build_phase3_full_items()`

#### 3.3.4 `patches/perf.py`

这个文件不直接改变主功能语义，但决定了你如何观察这套系统。

它对以下层统一加了 span / record：

- API server
- engine_core
- tp_worker

并额外支持 3 类 debug 输出：

- MM feature debug
- MM input order debug
- MM API prompt debug

### 3.4 推理流程 / API 流程 / 调度流程

这一部分按最终实际实现展开。

#### 3.4.1 API 流程总图

```text
Client
  -> OpenAI API server
    -> parser.parse_image / fetch_image
      -> phase1 source identity 解析
      -> phase3 local_ref 轻量构造
    -> renderer.render_messages
      -> 提取 local paths / source metadata
      -> 判断 phase3_local_mm_ready
      -> 如满足 phase3 本地条件:
           构造 grid-only mm_data
    -> OpenAIServingChat.render_chat_request
      -> 为每个 engine prompt 建 metadata queue
    -> ChatCompletionRequest.to_sampling_params
      -> queue 出队
      -> 写入 vllm_xargs
    -> InputProcessor.process_inputs
      -> 写入 sampling_params.extra_args
  -> engine core
  -> tp worker
```

#### 3.4.2 engine / scheduler 流程

当前代码没有重写 engine core scheduler 逻辑，而是：

1. 保留 stock scheduler
2. 通过 `sampling_params.extra_args` 带下去 metadata
3. 在 worker mm encoder 执行时，根据这些 metadata 决定：
   - 直接 encode
   - stock fallback

因此它是“**不改 scheduler 调度模型，只改 multimodal 数据的生产与消费路径**”。

#### 3.4.3 tp worker phase2/phase3 流程

以 `GPUModelRunner._execute_mm_encoder` 的 patch 为核心，worker 侧大致流程是：

```text
_execute_mm_encoder(scheduler_output)
  -> 遍历 scheduled_encoder_inputs
  -> 找出本 request 的 mm_features
  -> 只挑 image modality
  -> 依据 get_load_balance_assignment(sizes, tp_size)
     计算各 rank 负责的图片子集
  -> 从 request extra_args 中取本地路径 / source metadata
  -> 若不是纯 image，fallback
  -> 若 phase3 但不是 local-ready，fallback
  -> 若 local path 缺失，fallback
  -> 否则：
       ImageMediaIO.load_file(Path(path))
       processor.info.parse_mm_data(...)
       processor._apply_hf_processor_mm_only(...)
       MultiModalKwargsItems.from_hf_inputs(...)
  -> phase3:
       手动本 rank encode
       all_gather 汇总各 rank embeddings
       写回 encoder_cache[feature.identifier]
  -> phase2:
       与 stock item 做 tensor_equal 对比
       若一致则可回注
  -> 如果有 fallback 请求：
       临时替换 scheduler_output.scheduled_encoder_inputs
       调 stock original_execute()
```

### 3.5 phase3 direct encode 的真实实现逻辑

`phase3` 的关键不是“完全绕开 vLLM”，而是：

1. API 侧只保留轻量 planning 信息。
2. worker 侧重新从 local path 构造 multimodal inputs。
3. worker 手动调用模型的 multimodal embed 路径。
4. 最终将 encoder outputs 写回 stock encoder cache。

#### 3.5.1 API 侧只保留 grid 信息

`build_phase3_mm_data()` 会：

- 从 `_Phase3LocalImageRef` 里取宽高
- 借助 processor info 推导预处理后尺寸
- 只构造：
  - `image_grid_thw`

这说明 phase3 在 API 侧并不做完整像素预处理，只保留 downstream 需要的几何规划信息。

#### 3.5.2 worker 侧重建完整像素输入

worker 对自己负责的图片子集执行：

1. `ImageMediaIO.load_file`
2. `processor.info.parse_mm_data`
3. `processor._apply_hf_processor_mm_only`
4. `MultiModalKwargsItems.from_hf_inputs`

这一步才是真正的图像读取与 HF preprocess 下沉。

#### 3.5.3 worker 手动 encode

函数：

- `_phase3_encode_local_items_and_gather()`

关键逻辑：

- 暂时关闭 `model.use_data_parallel`
- 对本 rank local items 调 `model.embed_multimodal(**mm_kwargs_batch)`
- 检查输出数量
- 通过 `tensor_model_parallel_all_gather()` 汇总
- 重新按原始 image 顺序拼回

#### 3.5.4 encoder cache 回填

phase3 成功 direct encode 后，会：

- `self.encoder_cache[feature.identifier] = encoder_output`
- `self.maybe_save_ec_to_connector(...)`

这说明它没有绕开 stock 后续链路，而是把结果塞回 stock encoder cache，让后续推理仍建立在既有 vLLM 执行框架上。

#### 3.7.2 Chat request 层的队列

这些队列不是通用并发队列，而是为了解决：

- 一个 OpenAI request 可能映射到多个 engine prompts

因此这是**请求内 prompt 级 metadata 配对队列**。

- `get_load_balance_assignment(sizes, tp_size)`

worker 会按图片大小估计：

再计算：

- 每个 TP rank 分到哪些 image indices
- `gpu_sample_counts`
- `gpu_loads`

这就是当前 multimodal encode 的 rank 级负载切分逻辑。

## 5. 原始方案 VS 最终实现的差异对比

### 5.1 一致的地方

#### 5.1.1 一致点：采用 phase 演进而非一次性重写

原始设想：

- 先基线
- 再 hash
- 再路径透传
- 最后 direct encode

最终实现：

- 代码确实严格保留了 `phase0 ~ phase3` 分层体系

#### 5.1.2 一致点：不改 stock vLLM / vllm-ascend

原始设想：

- 不改 site-packages

最终实现：

- 通过 plugin + monkey patch 落地，未重打 wheel，未要求重新安装

#### 5.1.3 一致点：最终目标是 API server 下沉

原始设想：

- 让 worker 承担更多 multimodal 工作

最终实现：

- phase3 direct encode 确实把读图、hf preprocess、encode 主路径下沉到 worker

### 5.2 偏离的地方

#### 5.2.1 偏离点：phase3 没有变成“所有模态一刀切 direct encode”

原始可能设想：

- phase3 成为统一 direct encode 路径

最终实现：

- phase3 对不满足条件的请求走 fallback
- 尤其是：
  - 非 image 模态
  - 非 local-ready
  - rebuild 失败
  - 视频等不适合 direct encode 的情况

原因：

- 实际工程里必须优先保证稳定性

#### 5.2.2 偏离点：phase2 不只是“验证”，而变成 phase3 元数据透传基础设施

原始设想：

- phase2 是过渡阶段

最终实现：

- phase2 形成了稳定的 request plumbing 体系
- phase3 直接复用了这套路径

原因：

- metadata 透传链路一旦建好，就自然成为 phase3 的地基

#### 5.2.3 偏离点：phase1 不再只是 local hash 优化

原始设想：

- phase1 主要优化 local hash

最终实现：

- phase1 已承担：
  - local UUID
  - phase3 local ref 构造
  - transport-aware source metadata 建模

原因：

- API parser 最早接触 input URL，只能在这里做最自然的 source identity 建模

#### 5.2.4 偏离点：phase3 主线从多个实验方案收敛为单主线

原始阶段：

- 可能存在 `local-only` / `local-plus` 等并行实验

最终实现：

- 只保留 `phase3 direct encode`

原因：

- 多条实验路径会严重干扰接手与维护

### 5.3 为什么会偏离

从代码反推，偏离主要来自 4 种现实因素：

1. 稳定性约束
   - 所以需要 fallback
2. transport mode 复杂度
   - 所以必须引入 source metadata
3. phase3 多次试验后方案收敛
   - 所以旧入口被删除
4. 可观测性要求
   - 所以最终比原设想多出了大量 perf/debug patch

## 6. 关键技术细节

### 6.1 API 接口定义

#### 6.1.1 外部接口

当前工程不重写对外 API，继续复用 stock vLLM OpenAI 兼容接口：

- `GET /v1/models`
- `POST /v1/chat/completions`

请求格式仍是 OpenAI 风格 chat 请求。

#### 6.1.2 多模态输入形式

当前代码和验证实践表明，`phase3 direct encode` 当前明确关注并支持：

- `local_path`
- `http`
- `base64`

但要区分：

- `local_path` 是主要优化目标
- `http` 已支持但需分开评估
- `base64` 支持与串扰修复主要体现在 transport identity 层

#### 6.1.3 内部扩展字段

这套工程在内部 prompt / sampling params / request extra_args 中引入了多个扩展字段：

- `phase2_local_mm_paths`
- `phase2_image_source_metadata`
- `phase3_local_mm_ready`

这些字段不是外部 API 协议，而是内部 patch 协议。

### 6.2 错误处理

#### 6.2.1 API 侧错误处理

phase1 / phase2 的 API 侧 patch 总体策略是：

- 能回 stock 就回 stock
- 不在 parser 阶段贸然硬失败

例如：

- phase3 local ref 构造失败时，优先走 original parse/fetch

#### 6.2.2 worker 侧错误处理

worker 侧错误处理更明确：

- 如果 phase3 direct encode 路径失败，则记录 validate trace
- 能 fallback 的情况就回 stock `original_execute`

典型 fallback 条件：

- 非 image modality
- image_features 为空
- phase3 但 `phase3_local_mm_ready=False`
- `local_paths` 缺失
- `ImageMediaIO.load_file` / `parse_mm_data` / `hf_process` / `build_kwargs` 异常

#### 6.2.3 错误记录文件

主要落在：

- `VLLM_ASCEND_PHASE2_VALIDATE_FILE`

默认：

- `/tmp/vllm_ascend_phase2_validate.jsonl`

### 6.3 并发模型

#### 6.3.1 服务器并发

沿用 stock vLLM 的 OpenAI server 并发模型。

#### 6.3.2 async scheduling

由启动参数控制：

- 默认 `--async-scheduling`
- 也提供 `launch_registered_server_no_async.py`

#### 6.3.3 TP worker 并发

worker 侧仍遵循 stock TP 执行模型。

本工程只在 mm encoder 路径里增加：

- rank 级 local image 子集分工
- local encode 后 all_gather 汇总

### 6.4 显存优化

当前代码里的显存/内存优化主要是“沿用并配置 stock 能力”，而不是新写 allocator。

体现为：

- `--mm-processor-cache-type shm`
- `--mm-processor-cache-gb 20`
- `--gpu-memory-utilization 0.85`
- `PYTORCH_NPU_ALLOC_CONF=expandable_segments:True`
- `VLLM_ASCEND_ENABLE_PREFETCH_MLP=1`

phase3 的一个隐含收益是：

- API server 不再保存完整本地图像主处理结果
- 重型多模态张量构造更多转移到 worker

但它不等同于“总体显存一定下降”，更多是**热点位置和内存职责迁移**。

### 6.5 多模型支持

#### 6.5.1 当前实际适配重心

代码和文档明确聚焦：

- `Qwen3.5-4B`

并且 patch 中直接触达：

因此当前不能把它简单描述为“通用多模型方案”，更准确的说法是：

**这是以 Qwen3.5-4B 多模态服务为主的定向下沉工程。**

会导致：

- local_path 请求 400
- 视频或图片无法访问

#### 7.3.2 `http` 静态文件服务根目录不一致

会导致：

- `404`
- 继而引发上层 `500`

#### 7.3.3 切换输入模式时误以为“结果必须 bit-level 全一致”

当前实践表明：

- transport 串扰问题已可修复
- 但 MME 逐条预测仍可能有少量非确定性波动

因此需要区分：

- transport 串扰
- 模型推理非确定性

#### 7.3.4 phase3 不是所有 multimodal 请求都 direct encode

如果误以为“phase3 下所有请求都一定 direct encode”，就会误读日志。

真实情况是：

- 不满足条件就 fallback

#### 7.3.5 当前监控是文件式 trace

如果忘了清空 `/tmp/*.jsonl`，分析时容易混入旧记录。

### 7.4 特殊逻辑

#### 7.4.1 phase1 patch 是 phase2/3 的基础层

这点很关键。

虽然命名上叫 `phase1.py`，但它并不只服务 phase1。
在当前实现里，它同时承担：

- local stable UUID
- source identity
- phase3 local ref 构造

#### 7.4.2 `phase3_local_mm_ready` 是 phase3 主开关之一

这个布尔值决定：

- 是否允许走 phase3 local direct encode 语义

只要它是 `False`，worker 侧就会 fallback。

#### 7.4.3 transport metadata 是当前正确性的核心

当前 phase3 的一条关键经验是：

- local path 透传本身不够
- 必须显式区分 `media_mode`

#### 7.4.4 perf patch 侵入范围很大

`patches/perf.py` 覆盖面非常广。

它虽然主要是观测用途，但也意味着：

- 调试这套系统时，不应忽视 perf patch 对 call stack 的存在

### 7.5 代码特点总结

这套代码有几个鲜明特点：

1. 不是 fork vLLM，而是 patch vLLM。
2. phase 体系是叠加式，不是平行四套独立实现。
3. `phase3 direct encode` 的本质是“保留 stock scheduler，替换多模态数据生产/消费路径”。
4. 当前方案高度依赖 trace 文件来验证正确性。
5. 当前交付已经明显偏工程交付形态，而不只是实验脚本集合。

## 8. 总结：这套代码最终实现了什么？未实现什么？

### 8.1 最终实现了什么

当前 `0428` 最终实现了：

1. 一套**不修改 stock vLLM / vllm-ascend** 的插件化 phase0~3 交付工程。
2. 通过 `vllm.general_plugins` 机制在启动时自动打 patch。
3. `phase0`
   - 提供 stock 行为基线 + 统一性能观察能力。
4. `phase1`
   - 为本地图像建立稳定 UUID/hash 身份。
5. `phase2`
   - 打通 local path 和 source metadata 从 API -> engine -> worker 的透传链路。
6. `phase3 direct encode`
   - 将本地图像主处理链路下沉到 worker
   - worker 承担读图、HF preprocess、manual encode、cache 回填
   - 对不满足条件的路径自动 fallback 到 stock
7. 当前明确支持：
   - `local_path`
   - `http`
   - `base64` transport identity 隔离
8. 当前已提供：
   - 启动脚本
   - 设计文档
   - 性能脚本
   - 精度脚本
   - 输出比对脚本
   - trace/probe/debug 文件体系

### 8.2 当前没有实现什么

当前还没有实现或没有正式完成的内容包括：

1. 没有把 `phase3 direct encode` 做成“所有 multimodal 输入统一无 fallback”的最终形态。
2. 没有把这套方案泛化成“任意多模态模型可直接复用”的通用框架。
3. 没有自建：
   - 鉴权系统
   - 应用层限流器
   - 正式监控后台
4. 没有完全消除端到端结果的非确定性波动。
5. 没有把多图精度问题彻底优化完。

### 8.3 当前最准确的工程状态判断

如果要用一句话概括当前状态：

**`0428` 已经把 API server 下沉方案收敛成可运行、可验证、可维护的 `phase3 direct encode` 主线版本；当前主问题已从“服务能否稳定运行”转变为“多图精度与后续优化空间”。**
