## 1. 项目整体说明

### 1.1 项目名称 / 用途

项目可概括为：

`0428 Phase0~3 / Phase3 Direct Encode API Server 下沉交付工程`

用途是为 `Qwen3.5-4B` 多模态服务提供一套**不修改原始安装版 `vllm` / `vllm-ascend`** 的运行期增强方案，目标是逐步把原本压在 API server 上的多模态重处理逻辑下沉到 worker 侧。

这个目录不是一个独立重写的服务框架，而是一个**围绕 stock vLLM OpenAI API server 的插件化 patch 工程**。

它承担三类职责：

1. 交付可运行的 phase0 ~ phase3 启动方案。
2. 交付 `phase3 direct encode` 的当前主线实现。
3. 交付完整的精度、性能、对比、回归工具链。

### 1.2 基于什么框架

底座框架仍然是：

- `vLLM`
- `vllm-ascend`

真正启动的仍然是：

`python -m vllm.entrypoints.openai.api_server`

`0428/` 并没有替换这个入口，而是在它启动前通过 `vLLM general plugin` 机制完成 patch 注册。

### 1.3 整体架构

从目录和代码职责看，这套工程可以分成 5 层。

### 1.4 核心流程总览

#### 1.4.1 启动流程

```text

    -> export VLLM_ASCEND_API_OPT_PHASE=N
    -> export VLLM_PLUGINS=phase2_local_plugin,ascend

    -> python scripts/launch_registered_server.py
      -> import vllm_phase2_plugin
      -> vllm_phase2_plugin.register()
      -> runpy.run_module("vllm.entrypoints.openai.api_server")
```

#### 1.4.2 patch 注册流程

```text
register()
  -> apply_phase1_patch()
  -> if phase >= 2:
       apply_phase23_patches(enable_phase3 = phase >= 3)
  -> apply_perf_patches()
```

#### 1.4.3 请求处理总览

当前代码下，一个多模态请求会经过如下层次：

```text
Client
  -> OpenAI API Server
    -> chat parser / multimodal parser
    -> renderer
    -> OpenAI request -> sampling params
    -> engine input processor
    -> engine core scheduler
    -> TP worker
      -> phase2/phase3 worker-side multimodal path
      -> stock model execute / direct encode / fallback
  -> stream response
```

## 2. 原始设计目标

这一部分不是引用历史聊天，而是**根据当前代码反推最初想做什么**。

### 2.1 原始需求

从 `docs/00_project_scope.md`、`01_design.md`、`06_api_server_offload_design.md` 和 patch 结构反推，原始需求是：

1. 针对多模态大请求场景降低 API server 热点。
2. 保持 stock `vLLM` / `vllm-ascend` 不变。
3. 通过逐阶段 phase 演进，先建立基线，再逐步下沉图像处理。
4. 让 worker 承担更多 multimodal 读取、预处理和 encode 工作。
5. 保留可回退、可对比、可验证的工程形态。

### 2.2 业务场景假设

代码和文档里反复出现的目标负载是：

- 文本约 `10k` token
- 图片约 `40` 张
- 部署常态是 `TP4`
- `--enforce-eager`
- `mm shm cache`
- `mm encoder tp mode=data`

这说明原始方案不是面向“单张图 demo”，而是面向**高多图、高上下文、需要关注 TTFT/E2E 的真实服务场景**。

### 2.3 原始痛点

根据 docs 与 patch 命名，原始痛点主要是 API server 承担了太多 CPU 侧工作：

- 本地文件路径解析
- 图片读取
- 图片 decode
- HF multimodal processor 预处理
- multimodal hash 计算
- shm 相关 copy / cache 处理

这些逻辑在图片多、token 长时会成为 API server 热点。

### 2.4 原始预期能力

从 phase 划分可以推断最初预期能力是：

1. `phase0`
   - 作为精度与性能基线
2. `phase1`
   - 优化本地图像 hash 成本
3. `phase2`
   - 把本地路径透传到底层
4. `phase3`
   - 真正让 worker 接管 direct encode 主路径

### 2.5 原始预期架构

最原始的演进式架构可以反推为：

```text
phase0: 不动主链路，只做观察
phase1: 先降低 hash 成本
phase2: 先把 local path 透传到 worker
phase3: 再让 worker 直接做图像处理与 encode
```

### 2.6 每个 phase 的原始设计目标

#### 2.6.1 phase0

原始目标：

- 保持 stock 行为
- 加统一性能探针
- 建基线

原始主流程字符图：

```text
Client
  -> API server
    -> 读图 / decode / HF preprocess / mm hash / shm copy
  -> engine core
  -> tp worker
  -> response
```

#### 2.6.2 phase1

原始目标：

- 不动多模态主链路
- 只先优化本地图像 identity / hash

原始主流程字符图：

```text
Client
  -> API server
    -> 本地图片不再依赖昂贵内容 hash
    -> 改用稳定 UUID / 文件身份
  -> 其余链路维持 phase0
```

#### 2.6.3 phase2

原始目标：

- 打通“路径透传”
- worker 能感知 local path
- 验证按 vit-DP 分工读取本地图的正确性

原始主流程字符图：

```text
Client
  -> API server
    -> 正常做原始多模态处理
    -> 额外采集 local path 元数据
  -> engine core
    -> 保留 local path 到 request state
  -> tp worker
    -> 按 local path 读取自己负责的图片子集
```

#### 2.6.4 phase3

原始目标：

- 真正把图像主处理链路下沉到 worker
- API server 只保留轻量编排语义

原始主流程字符图：

```text
Client
  -> API server
    -> 仅保留 request parse / tokenizer / scheduling 相关语义
    -> 不再承担本地图像主预处理
  -> engine core
    -> 继续调度 mm encoder inputs
  -> tp worker
    -> load image
    -> hf preprocess
    -> direct encode
    -> 写回 encoder cache
```

### 2.7 原始方案中可能存在的分叉

从 `0427` 遗留文件名可推断，原始 phase3 并不只一个分支，还出现过：

- `phase3-local-only`
- `phase3-local-plus`

这说明最初一段时间里 phase3 方案并未收敛，可能存在多条实验路径并行探索。到了 `0428`，这件事已经被明确收敛：**只保留 `phase3 direct encode` 主线**。

## 3. 最终实际实现方案

这一部分完全基于当前 `0428` 代码，不讨论设想，只讨论真实落地。

### 3.1 核心模块结构

当前代码最终形成了一个“外部插件 + 运行期 monkey patch”的实现体系。

#### 3.1.1 入口发现

文件：

- `bundle/vllm_phase2_plugin-0.0.1.dist-info/entry_points.txt`

内容：

```text
[vllm.general_plugins]
phase2_local_plugin = vllm_phase2_plugin:register
```

这表示 vLLM 会在 general plugin 阶段调用：

`vllm_phase2_plugin.register`

#### 3.1.2 插件入口

文件：

- `bundle/vllm_phase2_plugin/register.py`

逻辑：

```python
def register():
    apply_phase1_patch()
    if phase_at_least(2):
        apply_phase23_patches(enable_phase3=phase_at_least(3))
    apply_perf_patches()
```

结论：

- phase1 patch 是通用前置 patch
- phase2/3 patch 只在 `phase >= 2` 时叠加
- perf patch 始终可启用

### 3.2 phase 选择与配置加载

#### 3.2.1 phase 读取

文件：

- `common/phase.py`

核心函数：

- `phase_value()`
- `phase_at_least(target)`
- `env_flag(name, default=False)`

行为：

- 从 `VLLM_ASCEND_API_OPT_PHASE` 读取 phase 值
- 支持数字字符串
- 支持形如 `phase3`
- 支持布尔风格字符串映射到 phase1

#### 3.2.2 启动配置加载

文件：

- `bundle/start_phase_server.sh`
- `scripts/launch_registered_server.py`

配置加载方式是**环境变量优先**。

主要参数包括：

- `MODEL_DIR`
- `HOST`
- `PORT`
- `TENSOR_PARALLEL_SIZE`
- `MM_PROCESSOR_CACHE_TYPE`
- `MM_PROCESSOR_CACHE_GB`
- `MM_ENCODER_TP_MODE`
- `GPU_MEMORY_UTILIZATION`
- `MAX_MODEL_LEN`
- `MAX_NUM_BATCHED_TOKENS`
- `ALLOWED_LOCAL_MEDIA_PATH`
- `ENABLE_ASYNC_SCHEDULING`

此外还会设置运行期 trace/probe 环境变量：

- `VLLM_ASCEND_PHASE2_VALIDATE_FILE`
- `VLLM_ASCEND_PERF_PROBE`
- `VLLM_ASCEND_PERF_PROBE_FILE`

#### 3.2.3 启动器最终传给 stock vLLM 的参数

`launch_registered_server.py` 会组装如下核心参数：

- `--model`

所以这套工程的部署方式，本质上是**用一个包装脚本替 stock vLLM 填好参数并打 patch**。

### 3.3 核心模块与关键类 / 函数

#### 3.3.1 `patches/phase1.py`

这是 API 入口侧最重要的 patch 文件，承担 4 类职责。

##### A. 稳定 local file UUID

关键函数：

- `stable_local_file_uuid(filepath: Path) -> uuid.UUID`

逻辑：

- 基于 `realpath + st_mtime_ns + st_size`
- 计算 md5
- 转成 UUID

用途：

- 避免按图像内容本体做重 hash
- 为本地图片提供稳定身份

##### B. transport/source identity 建模

关键函数：

- `_resolve_image_source_info(parser, image_url, uuid_str)`
- `_resolve_phase3_local_source_info(image_url)`

支持的 source mode：

- `local_path`
- `http`
- `base64`
- `unknown`

规则：

- `local_path`
  - key = `local_path:{realpath}|{mtime_ns}|{size}`
- `http`
  - key = `http:{canonical_url}`
- `base64`
  - key = `base64:req:{request_scope}:image:{idx}`

这是 `0428` 当前非常关键的实现点，因为它显式把 transport mode 纳入 identity。

##### C. phase3 API 轻量图像引用

关键类：

- `_Phase3LocalImageRef`

字段：

- `_phase2_local_path`
- `_phase2_media_mode`
- `_phase2_media_uuid`
- `_phase2_request_scope_key`
- `_phase2_source_key`
- `_phase3_width`
- `_phase3_height`

作用：

- 在 phase3 中，API server 不再立即把本地图读成完整图像数据
- 只构造一个轻量 reference，记录：
  - 本地路径
  - source metadata
  - 图像宽高

##### D. 打 patch 的具体位置

`apply_phase1_patch()` 改写了以下 stock 函数：

- `ImageMediaIO.load_file`
- `MultiModalContentParser.parse_image`
- `AsyncMultiModalContentParser._image_with_uuid_async`
- `MediaConnector.fetch_image`
- `MediaConnector.fetch_image_async`
- `InputPreprocessor._process_text`
- `InputPreprocessor._process_tokens`

这 7 个改写点意味着 phase1/phase3 的第一落点，实际上发生在：

- 图片 URL 解析
- 本地图片载入
- 异步 fetch
- request preprocess

#### 3.3.2 `patches/phase2.py`

这是整套方案真正承上启下的 patch 文件。

它覆盖了 5 个关键层面。

##### A. Renderer patch

函数：

- `patch_phase2_hf_renderer()`

改写：

- `HfRenderer.render_messages`
- `HfRenderer.render_messages_async`
- `BaseRenderer._process_multimodal`
- `BaseRenderer._process_tokens`

作用：

1. 从 `multi_modal_data` 中提取：
   - `phase2_local_mm_paths`
   - `phase2_image_source_metadata`
   - `phase3_local_mm_ready`
2. 在 phase3 + 全本地图片条件下，构造 `grid-only mm_data`
3. 把这些元数据继续塞回 prompt / inputs

这里的核心策略是：

- phase2：路径透传，不改主处理语义
- phase3：对 local_path 主链路可切换到 `build_phase3_mm_data()`

##### B. OpenAI chat request patch

函数：

- `patch_phase2_openai_chat()`

改写：

- `OpenAIServingChat.render_chat_request`
- `ChatCompletionRequest.to_sampling_params`

作用：

- 因为一个 chat request 可能渲染出多个 engine prompt
- 所以代码为每个 prompt 建了队列：
  - `_phase2_local_mm_paths_queue`
  - `_phase3_local_mm_ready_queue`
  - `_phase2_image_source_metadata_queue`
- 在 `to_sampling_params()` 时逐个出队，合并进 `vllm_xargs`

这是 phase2/3 把 API 侧元数据稳定带入 engine request 的关键桥梁。

##### C. Input processor patch

函数：

- `patch_phase2_input_processor()`

改写：

- `InputProcessor.process_inputs`

作用：

- 把 prompt 里带的：
  - `phase2_local_mm_paths`
  - `phase2_image_source_metadata`
  - `phase3_local_mm_ready`
 继续写入 `request.sampling_params.extra_args`

这样 worker 侧的 `req_state` 最终就可以从 `sampling_params.extra_args` 里把 metadata 取出来。

##### D. Qwen parser patch

函数：

- `patch_phase3_qwen_parser()`

改写：

- `Qwen2VLMultiModalDataParser._parse_image_data`

新增内部类：

- `_Phase3GridItems`

作用：

- 在 phase3 下，如果看到的是只含 `image_grid_thw` 而不含 `image_embeds` 的数据结构
- 就把它识别成合法的 image modality items

这一步是 phase3 grid-only API 侧策略能够接入 Qwen parser 的关键点。

##### E. Worker patch

函数：

- `patch_phase2_worker_validation()`

改写：

- `GPUModelRunner._batch_mm_inputs_from_scheduler`
- `GPUModelRunner._execute_mm_encoder`

这是当前整套方案的核心执行落点。

#### 3.3.3 `common/mm.py`

这个文件提供了 worker 与 renderer 的共享工具。

关键职责有 6 类：

1. JSONL trace 写入：
   - `append_jsonl()`
2. tensor / mm item 对比：
   - `tensor_equal()`
   - `summarize_mm_item()`
3. local path 标准化：
   - `normalize_local_mm_paths()`
   - `extract_local_mm_paths_from_mm_data()`
   - `extract_image_paths_for_request()`
4. source metadata 标准化：
   - `normalize_image_source_metadata()`
   - `extract_image_source_metadata_from_mm_data()`
   - `extract_image_source_metadata_for_request()`
5. phase3 API grid-only 构造：
   - `build_phase3_mm_data()`
6. phase3 worker 全量 item 重建辅助：
   - `build_phase3_full_items()`

#### 3.3.4 `patches/perf.py`

这个文件不直接改变主功能语义，但决定了你如何观察这套系统。

它对以下层统一加了 span / record：

- API server
- engine_core
- tp_worker

并额外支持 3 类 debug 输出：

- MM feature debug
- MM input order debug
- MM API prompt debug

### 3.4 推理流程 / API 流程 / 调度流程

这一部分按最终实际实现展开。

#### 3.4.1 API 流程总图

```text
Client
  -> OpenAI API server
    -> parser.parse_image / fetch_image
      -> phase1 source identity 解析
      -> phase3 local_ref 轻量构造
    -> renderer.render_messages
      -> 提取 local paths / source metadata
      -> 判断 phase3_local_mm_ready
      -> 如满足 phase3 本地条件:
           构造 grid-only mm_data
    -> OpenAIServingChat.render_chat_request
      -> 为每个 engine prompt 建 metadata queue
    -> ChatCompletionRequest.to_sampling_params
      -> queue 出队
      -> 写入 vllm_xargs
    -> InputProcessor.process_inputs
      -> 写入 sampling_params.extra_args
  -> engine core
  -> tp worker
```

#### 3.4.2 engine / scheduler 流程

当前代码没有重写 engine core scheduler 逻辑，而是：

1. 保留 stock scheduler
2. 通过 `sampling_params.extra_args` 带下去 metadata
3. 在 worker mm encoder 执行时，根据这些 metadata 决定：
   - 直接 encode
   - stock fallback

因此它是“**不改 scheduler 调度模型，只改 multimodal 数据的生产与消费路径**”。

#### 3.4.3 tp worker phase2/phase3 流程

以 `GPUModelRunner._execute_mm_encoder` 的 patch 为核心，worker 侧大致流程是：

```text
_execute_mm_encoder(scheduler_output)
  -> 遍历 scheduled_encoder_inputs
  -> 找出本 request 的 mm_features
  -> 只挑 image modality
  -> 依据 get_load_balance_assignment(sizes, tp_size)
     计算各 rank 负责的图片子集
  -> 从 request extra_args 中取本地路径 / source metadata
  -> 若不是纯 image，fallback
  -> 若 phase3 但不是 local-ready，fallback
  -> 若 local path 缺失，fallback
  -> 否则：
       ImageMediaIO.load_file(Path(path))
       processor.info.parse_mm_data(...)
       processor._apply_hf_processor_mm_only(...)
       MultiModalKwargsItems.from_hf_inputs(...)
  -> phase3:
       手动本 rank encode
       all_gather 汇总各 rank embeddings
       写回 encoder_cache[feature.identifier]
  -> phase2:
       与 stock item 做 tensor_equal 对比
       若一致则可回注
  -> 如果有 fallback 请求：
       临时替换 scheduler_output.scheduled_encoder_inputs
       调 stock original_execute()
```

### 3.5 phase3 direct encode 的真实实现逻辑

`phase3` 的关键不是“完全绕开 vLLM”，而是：

1. API 侧只保留轻量 planning 信息。
2. worker 侧重新从 local path 构造 multimodal inputs。
3. worker 手动调用模型的 multimodal embed 路径。
4. 最终将 encoder outputs 写回 stock encoder cache。

#### 3.5.1 API 侧只保留 grid 信息

`build_phase3_mm_data()` 会：

- 从 `_Phase3LocalImageRef` 里取宽高
- 借助 processor info 推导预处理后尺寸
- 只构造：
  - `image_grid_thw`

这说明 phase3 在 API 侧并不做完整像素预处理，只保留 downstream 需要的几何规划信息。

#### 3.5.2 worker 侧重建完整像素输入

worker 对自己负责的图片子集执行：

1. `ImageMediaIO.load_file`
2. `processor.info.parse_mm_data`
3. `processor._apply_hf_processor_mm_only`
4. `MultiModalKwargsItems.from_hf_inputs`

这一步才是真正的图像读取与 HF preprocess 下沉。

#### 3.5.3 worker 手动 encode

函数：

- `_phase3_encode_local_items_and_gather()`

关键逻辑：

- 暂时关闭 `model.use_data_parallel`
- 对本 rank local items 调 `model.embed_multimodal(**mm_kwargs_batch)`
- 检查输出数量
- 通过 `tensor_model_parallel_all_gather()` 汇总
- 重新按原始 image 顺序拼回

#### 3.5.4 encoder cache 回填

phase3 成功 direct encode 后，会：

- `self.encoder_cache[feature.identifier] = encoder_output`
- `self.maybe_save_ec_to_connector(...)`

这说明它没有绕开 stock 后续链路，而是把结果塞回 stock encoder cache，让后续推理仍建立在既有 vLLM 执行框架上。

### 3.7 并发、队列、调度如何实现

#### 3.7.1 API 并发模型

2. 提供 `launch_registered_server_no_async.py`
   - 强制 `--no-async-scheduling`

因此：

- 并发主模型：stock vLLM
- 本工程只负责是否打开 async scheduling

#### 3.7.2 Chat request 层的队列

在 `patch_phase2_openai_chat()` 中，当前工程新增了 3 个**请求内队列**：

- `_phase2_local_mm_paths_queue`
- `_phase3_local_mm_ready_queue`
- `_phase2_image_source_metadata_queue`

这些队列不是通用并发队列，而是为了解决：

- 一个 OpenAI request 可能映射到多个 engine prompts
- 每个 prompt 需要各自对应的 multimodal metadata

因此这是**请求内 prompt 级 metadata 配对队列**。

#### 3.7.3 engine core 调度

当前工程没有重写 scheduler 算法。

保留 stock：

- `scheduler.schedule()`
- `model_executor.execute_model(...)`
- `scheduler.update_from_output(...)`

在 perf patch 中只是加 timing record，不改变调度策略。

#### 3.7.4 worker 侧负载切分

真正与多模态切分有关的调度在：

- `get_load_balance_assignment(sizes, tp_size)`

worker 会按图片大小估计：

- `estimate_item_size(feature.data)`

再计算：

- 每个 TP rank 分到哪些 image indices
- `gpu_sample_counts`
- `gpu_loads`

这就是当前 multimodal encode 的 rank 级负载切分逻辑。

## 5. 原始方案 VS 最终实现的差异对比

### 5.1 一致的地方

#### 5.1.1 一致点：采用 phase 演进而非一次性重写

原始设想：

- 先基线
- 再 hash
- 再路径透传
- 最后 direct encode

最终实现：

- 代码确实严格保留了 `phase0 ~ phase3` 分层体系

#### 5.1.2 一致点：不改 stock vLLM / vllm-ascend

原始设想：

- 不改 site-packages

最终实现：

- 通过 plugin + monkey patch 落地，未重打 wheel，未要求重新安装

#### 5.1.3 一致点：最终目标是 API server 下沉

原始设想：

- 让 worker 承担更多 multimodal 工作

最终实现：

- phase3 direct encode 确实把读图、hf preprocess、encode 主路径下沉到 worker

### 5.2 偏离的地方

#### 5.2.1 偏离点：phase3 没有变成“所有模态一刀切 direct encode”

原始可能设想：

- phase3 成为统一 direct encode 路径

最终实现：

- phase3 对不满足条件的请求走 fallback
- 尤其是：
  - 非 image 模态
  - 非 local-ready
  - rebuild 失败
  - 视频等不适合 direct encode 的情况

原因：

- 实际工程里必须优先保证稳定性

#### 5.2.2 偏离点：phase2 不只是“验证”，而变成 phase3 元数据透传基础设施

原始设想：

- phase2 是过渡阶段

最终实现：

- phase2 形成了稳定的 request plumbing 体系
- phase3 直接复用了这套路径

原因：

- metadata 透传链路一旦建好，就自然成为 phase3 的地基

#### 5.2.3 偏离点：phase1 不再只是 local hash 优化

原始设想：

- phase1 主要优化 local hash

最终实现：

- phase1 已承担：
  - local UUID
  - phase3 local ref 构造
  - transport-aware source metadata 建模

原因：

- API parser 最早接触 input URL，只能在这里做最自然的 source identity 建模

#### 5.2.4 偏离点：phase3 主线从多个实验方案收敛为单主线

原始阶段：

- 可能存在 `local-only` / `local-plus` 等并行实验

最终实现：

- 只保留 `phase3 direct encode`

原因：

- 多条实验路径会严重干扰接手与维护

### 5.3 为什么会偏离

从代码反推，偏离主要来自 4 种现实因素：

1. 稳定性约束
   - 所以需要 fallback
2. transport mode 复杂度
   - 所以必须引入 source metadata
3. phase3 多次试验后方案收敛
   - 所以旧入口被删除
4. 可观测性要求
   - 所以最终比原设想多出了大量 perf/debug patch

## 6. 关键技术细节

### 6.1 API 接口定义

#### 6.1.1 外部接口

当前工程不重写对外 API，继续复用 stock vLLM OpenAI 兼容接口：

- `GET /v1/models`
- `POST /v1/chat/completions`

请求格式仍是 OpenAI 风格 chat 请求。

#### 6.1.2 多模态输入形式

当前代码和验证实践表明，`phase3 direct encode` 当前明确关注并支持：

- `local_path`
- `http`
- `base64`

但要区分：

- `local_path` 是主要优化目标
- `http` 已支持但需分开评估
- `base64` 支持与串扰修复主要体现在 transport identity 层

#### 6.1.3 内部扩展字段

这套工程在内部 prompt / sampling params / request extra_args 中引入了多个扩展字段：

- `phase2_local_mm_paths`
- `phase2_image_source_metadata`
- `phase3_local_mm_ready`

这些字段不是外部 API 协议，而是内部 patch 协议。

### 6.2 错误处理

#### 6.2.1 API 侧错误处理

phase1 / phase2 的 API 侧 patch 总体策略是：

- 能回 stock 就回 stock
- 不在 parser 阶段贸然硬失败

例如：

- phase3 local ref 构造失败时，优先走 original parse/fetch

#### 6.2.2 worker 侧错误处理

worker 侧错误处理更明确：

- 如果 phase3 direct encode 路径失败，则记录 validate trace
- 能 fallback 的情况就回 stock `original_execute`

典型 fallback 条件：

- 非 image modality
- image_features 为空
- phase3 但 `phase3_local_mm_ready=False`
- `local_paths` 缺失
- `ImageMediaIO.load_file` / `parse_mm_data` / `hf_process` / `build_kwargs` 异常

#### 6.2.3 错误记录文件

主要落在：

- `VLLM_ASCEND_PHASE2_VALIDATE_FILE`

默认：

- `/tmp/vllm_ascend_phase2_validate.jsonl`

### 6.3 并发模型

#### 6.3.1 服务器并发

沿用 stock vLLM 的 OpenAI server 并发模型。

#### 6.3.2 async scheduling

由启动参数控制：

- 默认 `--async-scheduling`
- 也提供 `launch_registered_server_no_async.py`

#### 6.3.3 TP worker 并发

worker 侧仍遵循 stock TP 执行模型。

本工程只在 mm encoder 路径里增加：

- rank 级 local image 子集分工
- local encode 后 all_gather 汇总

### 6.4 显存优化

当前代码里的显存/内存优化主要是“沿用并配置 stock 能力”，而不是新写 allocator。

体现为：

- `--mm-processor-cache-type shm`
- `--mm-processor-cache-gb 20`
- `--gpu-memory-utilization 0.85`
- `PYTORCH_NPU_ALLOC_CONF=expandable_segments:True`
- `VLLM_ASCEND_ENABLE_PREFETCH_MLP=1`

phase3 的一个隐含收益是：

- API server 不再保存完整本地图像主处理结果
- 重型多模态张量构造更多转移到 worker

但它不等同于“总体显存一定下降”，更多是**热点位置和内存职责迁移**。

### 6.5 多模型支持

#### 6.5.1 当前实际适配重心

代码和文档明确聚焦：

- `Qwen3.5-4B`

并且 patch 中直接触达：

- `Qwen2VLMultiModalDataParser`
- `Qwen3VLMultiModalProcessor`

这说明当前方案虽然底层依赖 stock vLLM，但 patch 实际带有明显的 Qwen 多模态模型倾向。

可泛化部分：

- 启动器

强模型绑定部分：

- Qwen parser patch

因此当前不能把它简单描述为“通用多模型方案”，更准确的说法是：

**这是以 Qwen3.5-4B 多模态服务为主的定向下沉工程。**

### 7.3 可能的坑

#### 7.3.1 `ALLOWED_LOCAL_MEDIA_PATH` 范围不对

会导致：

- local_path 请求 400
- 视频或图片无法访问

#### 7.3.2 `http` 静态文件服务根目录不一致

会导致：

- `404`
- 继而引发上层 `500`

#### 7.3.3 切换输入模式时误以为“结果必须 bit-level 全一致”

当前实践表明：

- transport 串扰问题已可修复
- 但 MME 逐条预测仍可能有少量非确定性波动

因此需要区分：

- transport 串扰
- 模型推理非确定性

#### 7.3.4 phase3 不是所有 multimodal 请求都 direct encode

如果误以为“phase3 下所有请求都一定 direct encode”，就会误读日志。

真实情况是：

- 不满足条件就 fallback

#### 7.3.5 当前监控是文件式 trace

如果忘了清空 `/tmp/*.jsonl`，分析时容易混入旧记录。

### 7.4 特殊逻辑

#### 7.4.1 phase1 patch 是 phase2/3 的基础层

这点很关键。

虽然命名上叫 `phase1.py`，但它并不只服务 phase1。
在当前实现里，它同时承担：

- local stable UUID
- source identity
- phase3 local ref 构造

#### 7.4.2 `phase3_local_mm_ready` 是 phase3 主开关之一

这个布尔值决定：

- 是否允许走 phase3 local direct encode 语义

只要它是 `False`，worker 侧就会 fallback。

#### 7.4.3 transport metadata 是当前正确性的核心

当前 phase3 的一条关键经验是：

- local path 透传本身不够
- 必须显式区分 `media_mode`

#### 7.4.4 perf patch 侵入范围很大

`patches/perf.py` 覆盖面非常广。

它虽然主要是观测用途，但也意味着：

- 调试这套系统时，不应忽视 perf patch 对 call stack 的存在

### 7.5 代码特点总结

这套代码有几个鲜明特点：

1. 不是 fork vLLM，而是 patch vLLM。
2. phase 体系是叠加式，不是平行四套独立实现。
3. `phase3 direct encode` 的本质是“保留 stock scheduler，替换多模态数据生产/消费路径”。
4. 当前方案高度依赖 trace 文件来验证正确性。
5. 当前交付已经明显偏工程交付形态，而不只是实验脚本集合。

## 8. 总结：这套代码最终实现了什么？未实现什么？

### 8.1 最终实现了什么

当前 `0428` 最终实现了：

1. 一套**不修改 stock vLLM / vllm-ascend** 的插件化 phase0~3 交付工程。
2. 通过 `vllm.general_plugins` 机制在启动时自动打 patch。
3. `phase0`
   - 提供 stock 行为基线 + 统一性能观察能力。
4. `phase1`
   - 为本地图像建立稳定 UUID/hash 身份。
5. `phase2`
   - 打通 local path 和 source metadata 从 API -> engine -> worker 的透传链路。
6. `phase3 direct encode`
   - 将本地图像主处理链路下沉到 worker
   - worker 承担读图、HF preprocess、manual encode、cache 回填
   - 对不满足条件的路径自动 fallback 到 stock
7. 当前明确支持：
   - `local_path`
   - `http`
   - `base64` transport identity 隔离
8. 当前已提供：
   - 启动脚本
   - 设计文档
   - 性能脚本
   - 精度脚本
   - 输出比对脚本
   - trace/probe/debug 文件体系

### 8.2 当前没有实现什么

当前还没有实现或没有正式完成的内容包括：

1. 没有把 `phase3 direct encode` 做成“所有 multimodal 输入统一无 fallback”的最终形态。
2. 没有把这套方案泛化成“任意多模态模型可直接复用”的通用框架。
3. 没有自建：
   - 鉴权系统
   - 应用层限流器
   - 正式监控后台
4. 没有完全消除端到端结果的非确定性波动。
5. 没有把多图精度问题彻底优化完。

### 8.3 当前最准确的工程状态判断

如果要用一句话概括当前状态：

**`0428` 已经把 API server 下沉方案收敛成可运行、可验证、可维护的 `phase3 direct encode` 主线版本；当前主问题已从“服务能否稳定运行”转变为“多图精度与后续优化空间”。**
