# 开发日志

## 2026-04-28：phase3 direct encode 多输入模式串扰修复

### 背景

`0428` 目录已经将 `phase3 direct encode` 固化为当前唯一继续演进的 `phase3` 主方案，
并且已经完成：

- `tp4` 启动与稳定运行
- `local_path` 支持
- `http` 支持
- 视频 fallback 到 stock 路径
- `L0 / L0.5 / MME / MMBench` 多轮精度回归

但在继续做 `http / base64 / local_path` 三种输入模式切换测试时，
暴露出一个新的系统性问题：

- 同一个服务进程内，先跑 `http`，再跑 `base64` 或 `local_path`
- 会偶发出现把历史 `http` 输入残留状态错误复用到后续请求的现象
- 具体外显包括：
  - `base64 MMBench` 请求中错误访问 `http://127.0.0.1:9000/mmbench/*.jpg`
  - 返回 `404`
  - 上层继续放大后出现 `500 InternalServerError`
  - 某些场景下会进一步触发 `encoder cache miss`

### 原方案的问题

原始 patch 的重点在于两件事：

1. 为 `local_path` 透传本地路径，支撑 `phase3 direct encode`
2. 为 worker 侧 direct encode 提供足够的定位信息

这套实现对 `local_path -> worker direct encode` 主链路是成立的，
但它存在一个隐含前提：

- “同一张图的传输方式不会变化”

而精度测试恰好打破了这个前提：

- 同一个数据集文件
- 可能先以 `http://127.0.0.1:9000/mmbench/1986.jpg` 发起
- 再以 `data:image/...;base64,...` 发起
- 再以 `file:///.../mmbench/1986.jpg` 或本地路径发起

旧方案的问题不是 direct encode 算法本身，
而是 **传输层 identity 没有被显式建模并传到底层**。

旧 patch 更多是在传：

- `_phase2_local_path`
- `phase2_local_mm_paths`
- `phase3_local_mm_ready`

但没有稳定传递：

- 当前输入到底是 `local_path / http / base64` 中的哪一种
- 它的 source key 是什么
- 哪些 key 允许跨请求复用
- 哪些 key 只允许 request-scope 使用

这样一来，只要底层某处还存在“按逻辑名、相对路径、历史 url 映射、旧请求残留状态”做弱关联的机会，
就有可能把：

- `mmbench/1986.jpg -> http://127.0.0.1:9000/mmbench/1986.jpg`

错误复用到后续 `base64` 或 `local_path` 请求上，
从而形成跨输入模式串扰。

### 已观测到的现象

在 `0428 phase3 direct encode tp4` 环境下，已经确认：

1. `base64 MMBench` 曾出现 `404/500`
   现象是请求不该再访问本地静态 HTTP 服务，但日志里仍出现
   `127.0.0.1:9000/mmbench/*.jpg`。

2. `local_path MMBench` 曾出现 `500`
   放大后表现为 `encoder cache miss / EngineDeadError / 500`。

3. 做“切换输入模式前重启服务”后，问题可消失
   说明这是 **进程内跨请求状态污染/弱 key 复用问题**，
   而不是数据集本身错误。

### 已验证的临时规避方案

临时规避方案已经验证有效：

- 在切换多模态输入模式前重启服务

重启后已经验证：

- `base64 MMBench` 可跑通，不再出现错误访问 `9000/mmbench/*.jpg`
- `base64 MMBench` 不再出现 `404 / 500 / encoder cache miss`
- `local_path MMBench` 可跑通，不再出现 `500 / EngineDeadError`

这说明当前问题不是模型精度问题，
而是输入模式切换时的 transport-layer identity 污染问题。

### 修复目标

修复目标不是“让不同输入模式互相复用同一份缓存”，而是：

1. 明确区分 `local_path / http / base64`
2. 禁止不同输入模式之间的弱关联复用
3. 保持 `phase3 direct encode` 对 `local_path` 和可支持 `http` 路径的主能力
4. 不修改 vLLM 源码，只修改 `0428/patch`
5. 不引入高成本内容 hash

### 为什么不采用内容 hash

这里不采用“按图像内容本体做 hash”的原因有三点：

1. 成本高
   对每张图都读取完整内容再 hash，会明显增加 API server 热点负担，
   与当前“把热点下沉、让 API server 只保留编排职责”的目标相冲突。

2. 真实业务收益低
   真实生产里，同一份图像数据同时既用 `local_path` 又用 `http`
   又用 `base64` 去请求，通常不是主流场景。

3. 当前问题本质不是“同内容去重失败”
   而是“不同输入模式被错误混用”。
   因此更应该修 transport identity，
   而不是做昂贵内容去重。

### 新方案

本次修复采用 **source-based identity**：

- 不按图像内容做 hash
- 按“输入模式 + 来源信息”生成稳定 key

具体规则如下。

#### 1. local_path

`local_path` 的 source key 采用：

- `media_mode=local_path`
- `realpath`
- `stat.st_size`
- `stat.st_mtime_ns`

目标：

- 同一路径文件变更后 key 会变化
- 不同路径不会误判为同一资源
- 不需要读取图像全部内容

#### 2. http

`http` 的 source key 采用：

- `media_mode=http`
- canonical url

目标：

- 不与 `local_path` 共用 identity
- 不与 `base64` 共用 identity

#### 3. base64

`base64` 不做跨请求稳定缓存 key，
只做 **request-scope key**：

- `media_mode=base64`
- `request_scope`
- `image index`

例如：

- `req:<request_id>:image:0`
- `req:<request_id>:image:1`

目标：

- `base64` 只在单请求内部保持一致
- 不与历史 `http` 或 `local_path` 请求发生弱关联

### 关键设计原则

#### 原则 1：transport mode 是 identity 的一部分

即使它们最终指向“同一张图”，下面三种输入也视为不同 source：

- `local_path`
- `http`
- `base64`

不允许仅因为逻辑名相同，例如 `mmbench/1986.jpg`，
就在不同模式之间复用。

#### 原则 2：禁止跨模式 fallback

后续任何映射、回填、恢复、兜底逻辑都必须满足：

- 当前请求的 `media_mode`
- 已存状态的 `media_mode`

二者一致时才允许复用；
只要 mode 不一致，就必须当作 miss 处理。

#### 原则 3：bare logical name 不能作为稳定 key

以下信息都不能单独作为稳定 identity：

- `mmbench/1986.jpg`
- 相对路径
- 不带 mode 的 url 尾部

这些值最多只能作为调试信息，不能作为跨请求复用主键。

### patch 层落点

本次修改只允许发生在 `0428` 下，不修改 vLLM 源码。

预计落点：

- `bundle/vllm_phase2_plugin/patches/phase1.py`
- `bundle/vllm_phase2_plugin/common/mm.py`
- 如有必要，补充 `patches/phase2.py` 的 metadata 透传

### 方案摘要

最终方案可概括为：

1. 在 parser 入口识别 image 输入模式
2. 生成带 mode 的 `source_key`
3. 为 image 显式生成 `uuid`
4. 将 `uuid/source metadata` 随 `multi_modal_uuids` 与 patch metadata 一起向后透传
5. `base64` 使用 request-scope uuid
6. `local/http/base64` 之间禁止通过弱 identity 互相复用

### 回归验证要求

修复完成后，至少需要确认：

1. 不重启服务，先跑 `http` 再跑 `base64 MMBench`
   不应再访问 `127.0.0.1:9000/mmbench/*.jpg`
   不应再出现 `404 / 500`

2. 不重启服务，先跑 `http` 再跑 `local_path`
   不应把 HTTP 历史状态错误复用到本地路径请求

3. `phase3 direct encode tp4` 的基本精度能力不回退
   重点关注：
   - `L0`
   - `L0.5`
   - `MME`
   - 必要时复测 `MMBench`

### 当前结论

到本次日志记录时，已经形成明确结论：

- 问题属于多模态输入 transport identity 串扰
- 不是 direct encode 主算法错误
- 不需要修改 vLLM 源码
- 最合理的修复方式是：
  - 在 `0428` patch 层显式生成 mode-aware uuid/source key
  - 禁止跨模式 fallback
  - `base64` 只做 request-scope 复用

## 2026-04-28：phase4 HTTP 输入本地缓存池优化

### 背景

`0428` 当前已经把 `phase3 direct encode` 固化为主方案，但它对不同输入模式的收益并不一致：

- `local_path` 已经能稳定复用 worker 侧 direct encode 主链路
- `http` 虽然功能上可用，但更多还是 stock 行为兼容

因此需要引入新的 `phase4`，专门解决：

`让 http 输入也能复用 phase3 direct encode 的收益。`

### 反推后的问题本质

`phase3 direct encode` 的核心前提是：

- API 侧能把图片输入表达成“可透传本地路径的 phase3 引用”

`local_path` 天然满足这个条件；
而 `http` 不满足，所以在 `phase3` 中：

- 不能设置稳定的 `_phase2_local_path`
- `phase3_local_mm_ready` 不会被置为 `true`
- worker 就无法复用现有的本地路径 direct encode 主链路

### 方案选择

这里有两个备选方案：

1. worker 自己下载远端 http 资源
2. API server 先下载到本地缓存池，再当作 local_path 走 phase3

最终选择方案2，原因是：

1. 可以最大化复用现有 `phase3 direct encode`
2. 下载、锁、TTL、大小限制都更容易统一收敛
3. 风险更低，不需要在 worker 再发明一条远端抓图链路

### 新方案定义

`phase4 = API server 本地 HTTP cache pool + materialize 到本地文件 + 复用 phase3 direct encode`

也就是：

1. 识别 `http/https` 图片 URL
2. 以 canonical URL 计算 cache key
3. 命中则复用缓存
4. miss 则下载到本地缓存目录
5. 下载成功后构造 phase3-style local image ref
6. worker 继续走原有 direct encode

### 关键设计原则

#### 原则 1：只在 phase4 生效

所有新逻辑只允许在：

```text
VLLM_ASCEND_API_OPT_PHASE >= 4
```

时启用，保证 `phase0 ~ phase3` 完全不受影响。

#### 原则 2：transport identity 不变

缓存到本地后，仍保留：

- `media_mode=http`
- `image_url=<original http url>`

只是额外补上：

- `_phase2_local_path=<cached local file>`

这样既能让 worker 复用本地 direct encode，
又不会把它错误伪装成用户本来就是 `local_path`。

#### 原则 3：不做内容 hash

仍然坚持“按来源标识，不按图像内容全文 hash”的方向：

- `cache_key = sha1(canonical_http_url)`

原因：

1. 成本更低
2. 更符合真实业务中“同 URL 重复请求”的场景
3. 避免重新把热点拉回 API server

### 本次代码改动

#### `bundle/vllm_phase2_plugin/patches/phase1.py`

新增或补齐：

1. `phase4` 环境开关
2. HTTP cache 目录、TTL、超时、大小限制、chunk 大小、UA 配置
3. 基于文件锁的 HTTP 物化逻辑
4. `http -> local cached file -> phase3-style ref` 组装逻辑
5. 在下面几个入口接线：
   - `MultiModalContentParser.parse_image`
   - `AsyncMultiModalContentParser._image_with_uuid_async`
   - `MediaConnector.fetch_image`
   - `MediaConnector.fetch_image_async`

#### `bundle/vllm_phase2_plugin/common/mm.py`

补充 `image_url` 元数据透传，方便 trace/validate/debug。

#### `bundle/start_phase4_server.sh`

新增 `phase4` 启动脚本，便于直接拉起：

```bash
export VLLM_ASCEND_API_OPT_PHASE=4
```

### 预期收益

完成后，`http` 输入将具备两层收益：

1. 相同 URL 的重复请求可以命中 API 侧本地缓存
2. materialize 完成后，worker 可以复用已有的 `phase3 direct encode`
